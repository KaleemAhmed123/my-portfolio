01
ETL

JS ETL platform story

Bi-directional synchronization across SAP, Salesforce, and Ecommerce.

The resume claims a production-grade JS ETL platform with file-driven ingestion, REST propagation, merged outbound acknowledgement files, parallel processing, and 80-85 percent manual reconciliation reduction. Be ready to explain it like a system design.

Extract: receive SAP JSON payload files, validate schema, split records, attach source metadata.
Transform: normalize fields, map IDs, convert statuses, validate required business rules.
Load: UPSERT into Salesforce and Ecommerce through REST APIs with retries and idempotency.
Acknowledge: generate merged outbound ack files with success/failure per record.
Operate: logs, trace IDs, retry reports, partial-success handling, manual review queue.
02
Consistency

Source-aware idempotent UPSERTs

The core correctness claim in the integration platform.
ConceptMeaningWhy it matters
Composite keySAP ID + Salesforce ID + Ecommerce ID or a stable natural keyPrevents duplicates when the same entity arrives from multiple systems
Source awarenessKnow which system sent the update and which fields it ownsPrevents lower-authority systems from overwriting authoritative data
Transaction boundaryGroup local DB changes atomicallyAvoids half-updated local state
Partial successSome records or destinations can fail while others succeedBatch does not need to fully fail; failures become retryable units
Fault isolationBad record does not stop the entire fileHigh-throughput integrations survive dirty data
"How do you prevent duplicate records in a sync pipeline?"

"I use stable external IDs and composite unique constraints, then perform idempotent UPSERTs instead of blind inserts. I keep a mapping table between SAP, Salesforce, and Ecommerce IDs, record the source and event ID, and make retries safe. If one destination fails, I persist the failed operation with enough context to retry without reprocessing successful work."

03
Payments

Razorpay and Stripe fundamentals

Payments are distributed systems with money attached.

Payment Intent/Order

Create server-side amount/currency/order reference. Never trust amount from client after creation.

Idempotency

Use idempotency keys so retries do not create duplicate charges or duplicate internal orders.

Webhook Verification

Verify provider signature. Treat webhook as source of truth for final payment state.

Reconciliation

Compare provider records with internal orders, payouts, refunds, and failed webhooks.

Payment rule

The client can start payment, but the server verifies final status with the provider and updates internal state idempotently. Never mark paid only because the frontend says payment succeeded.

05
Shipping

Shiprocket and external APIs

Shipping APIs fail in messy real-world ways.

Rate Limits

Throttle provider calls and retry 429 with backoff. Queue non-urgent sync jobs.

Status Mapping

Provider statuses must map to internal states. Unknown statuses should be logged and reviewed.

Tracking Updates

Use webhooks where available, plus periodic polling as fallback for missed events.

Partial Failure

Order can be paid but shipment creation can fail. Persist state and retry shipment independently.

06
Webhooks

Webhook handling checklist

Providers retry; your endpoint must be safe.
Verify signature: reject forged requests before processing.
Deduplicate: store provider event ID and ignore replays.
Respond fast: enqueue heavy work and return 2xx after durable acceptance.
Idempotent state machine: payment_succeeded twice should not double-credit wallet.
Audit: store raw event payload, parsed event, processing status, retries, and errors.
Recovery: reconciliation job should find missed or failed events.
"What if the payment webhook arrives before your checkout API response?"

"That is normal in distributed systems. The webhook handler should be able to find the order by provider reference/idempotency key, or temporarily store the event as pending until the order exists. State transitions must be idempotent and order-independent where possible."

07
Deep Reference

Integration, commerce, and payment reference

Use this when building or explaining real systems with external dependencies.

The main idea

External integrations are unreliable by default: APIs time out, webhooks arrive late or twice, payloads change, providers rate-limit, and partial success is common. Strong engineers design integrations around idempotency, durable state, reconciliation, observability, and manual recovery paths.

ETL
Data Sync

Production ETL architecture

How to explain the SAP/Salesforce/Ecommerce platform in detail.
File ingestion service detects or receives SAP JSON files, assigns batch ID, validates file-level schema, and stores original payload for replay/debugging.
Parser splits file into records, attaches source metadata, validates required fields, and writes accepted/rejected records into a durable staging table.
Transformer normalizes field names, data types, enums, timestamps, currency, address format, and external identifiers.
Resolver uses mapping table to connect SAP ID, Salesforce ID, Ecommerce ID, and internal canonical entity ID.
Loader performs idempotent UPSERTs to local DB and downstream APIs. Each record has independent status: pending, success, failed, retrying, skipped.
Acknowledgement generator merges per-record results into outbound ack files with success/failure reason and external references.
Operations dashboard shows batch status, record failures, retry count, manual review items, and reconciliation mismatches.

MAP
Identity Mapping

Canonical IDs and source-aware UPSERTs

The heart of cross-system consistency.

Canonical entity model

Create an internal canonical ID for each entity and map all external IDs to it. This prevents the system from treating the same customer/product/order as three different records.

Mapping table idea
entity_identity_map
- canonical_id
- entity_type        -- customer, product, order
- sap_id
- salesforce_id
- ecommerce_id
- source_of_truth
- last_seen_at
- created_at
- updated_at

Field ownership

Source-aware means knowing which system is allowed to update which fields. For example, SAP may own inventory and SKU, Ecommerce may own storefront description, Salesforce may own sales/account metadata.

Conflict resolution

Use deterministic rules: source priority, updated_at only from trusted source, manual review for conflicting high-risk fields, and audit log for every overwrite.

PAY
Payments

Payment lifecycle in detail

Payments require state machines, not boolean flags.
Client starts checkout. Server recalculates amount from trusted cart/product data and creates internal pending order.
Server creates provider payment order/intent and stores provider reference, amount, currency, user, and idempotency key.
Client completes payment using provider SDK. Frontend result is treated as untrusted until server verifies.
Provider webhook arrives. Server verifies signature, deduplicates event ID, fetches/validates provider status if needed, and updates payment state.
Order transitions to paid only once. Downstream events trigger shipment creation, seller wallet credit lock, invoice, and notification.
Reconciliation job compares internal payment states with provider reports to catch missed webhooks or manual provider changes.

LED
Wallet

Seller wallet and ledger design

Balances are derived facts; ledger is the source of truth.

Ledger entries

Use append-only entries for every credit/debit. Each entry has amount, currency, seller ID, order ID, reason, status, idempotency key, and created_by/system actor.

Ledger table shape
wallet_ledger
- id
- seller_id
- type              -- credit, debit, hold, release, payout
- amount
- currency
- reference_type    -- order, refund, payout
- reference_id
- idempotency_key
- status            -- pending, available, reversed, paid_out
- created_at

Available vs locked balance

When an order is paid, seller earnings may go to locked balance until return/refund window passes. After the lock period, funds move to available balance. Payouts debit available balance only.

Reconciliation

Periodically recompute balances from ledger and compare with stored wallet balance. Any mismatch should alert and block payouts until reviewed.

WH
Webhooks

Webhook reliability pattern

A webhook endpoint is an ingestion system.
Webhook handler algorithm
1. Read raw body exactly as provider signed it.
2. Verify signature and timestamp tolerance.
3. Parse event type and provider event ID.
4. Insert event ID into webhook_events with unique constraint.
5. If duplicate, return 200 immediately.
6. Store raw payload and mark status = received.
7. Enqueue processing job or process quickly.
8. Handler updates domain state idempotently.
9. Mark event processed or failed with error.
10. Reconciliation catches anything missed.
"Why return 200 even for duplicate webhook?"

Because the provider only needs to know that your system has accepted or already processed the event. Returning an error for duplicates causes more retries. Duplicate delivery is normal, so deduplicate internally and return success when safe.

REC
Reconciliation

Reconciliation and manual recovery

The system must recover from unknown outcomes.
Payment reconciliation: compare provider captured/refunded payments with internal order/payment records.
Wallet reconciliation: recompute seller balances from ledger and compare with stored aggregates.
Shipment reconciliation: poll provider for shipments without recent webhook updates.
ETL reconciliation: compare record counts, success/failure statuses, and external IDs across SAP/Salesforce/Ecommerce.
Manual review: failed records need clear error reason, retry button, raw payload, transformed payload, and audit history.
ANS
Interview Answers

Integration answers worth memorizing

These come up often in project deep-dives.
"How do you handle partial success in third-party integrations?"

I model each record or downstream operation independently with its own status. Successful items are committed and acknowledged; failed items store the error, retry count, and next retry time. The batch status becomes completed_with_errors if needed. This avoids throwing away good work and lets operations retry only failed records.

"What is your strategy for provider timeouts?"

A timeout means unknown outcome, not guaranteed failure. For create/payment operations I use idempotency keys or provider reference IDs, then query provider state before retrying blindly. Retries use backoff and a maximum attempt count, and unresolved cases go to manual review or reconciliation.

"How would you prevent double payout?"

Use an immutable ledger, unique payout request IDs, transaction boundaries, row locks on wallet/account rows, idempotency keys for payout provider calls, and status transitions that allow payout execution only once. Reconciliation must compare payout provider records against internal ledger entries.
