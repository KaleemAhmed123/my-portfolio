Distributed Systems Basics

Multiple servers, partial failures, and why the network always lies

Core Concept

Once your system spans multiple machines, a whole new class of failures emerges. A server can be slow, not dead. A request might be received but the response lost. The same request might be processed twice. Clocks on different machines drift apart. These aren't edge cases — they're normal production conditions you must design around.

The famous Fallacies of Distributed Computing: the network is reliable, latency is zero, bandwidth is infinite, the network is secure, topology doesn't change. All of these are false — every single one. Your system must be designed assuming each will occasionally be violated.

🎭 Analogy

Running a distributed system is like managing workers in different cities who can only communicate by postcards. A postcard might arrive late, arrive twice, never arrive, or arrive out of order. You can never be 100% sure if your colleague received your last message. Every decision must account for that uncertainty. This isn't a bug — it's the fundamental nature of distributed communication.

CAP Theorem — The Fundamental Trade-off

A distributed system can only guarantee two of three properties simultaneously. Since network partitions always happen (cables fail, switches crash), you're really choosing between C and A:

C — Consistency

Every read sees the most recent write. All nodes return same data. Refuse requests during partition to avoid stale reads.

A — Availability

Every request gets a response — not necessarily the latest data. Serve potentially stale data during partition rather than error.

P — Partition Tolerance

System keeps working when network between nodes fails. Non-negotiable in any real distributed system.

ChoiceBehavior during partitionExamples
CPRefuse reads/writes to avoid stale data. Returns error.PostgreSQL, HBase, ZooKeeper, etcd
APServe potentially stale data. Eventually consistent.DynamoDB, Cassandra, CouchDB

Code Example — Idempotency Key

Node.jsIdempotency key — safe retries in distributed systems
// Problem: request succeeds server-side but client never gets response
// Client retries → duplicate order created → customer charged twice
// Solution: idempotency key deduplicates at the server

app.post('/orders', async (req, res) => {
  const idempotencyKey = req.headers['idempotency-key'];
  if (!idempotencyKey) {
    return res.status(400).json({ error: 'Idempotency-Key header required' });
  }

  const lockKey = `idem:${idempotencyKey}`;
  const existing = await redis.get(lockKey);

  if (existing) {
    // Duplicate request — return cached result, don't reprocess
    return res.status(200).json(JSON.parse(existing));
  }

  const order = await createOrder(req.body);
  const response = { orderId: order.id, status: 'created' };

  // Cache result for 24h — client can safely retry within that window
  await redis.setex(lockKey, 86400, JSON.stringify(response));
  res.status(201).json(response);
});

// Client: generate UUID ONCE before first attempt, reuse on all retries
const key = crypto.randomUUID();
await retryWithBackoff(() =>
  fetch('/orders', {

⚡ Production Tips
  • Design all mutation endpoints (payments, orders) to be idempotent via an idempotency key. Safe retries are the foundation of resilient distributed systems.
  • Never compare timestamps from different servers for ordering — clocks drift. Use logical clocks or monotonically increasing sequence IDs from a central source.
  • Any external service call can fail partially. Always design the recovery path: "What if this call succeeds on their side but I never get the response?"
  • Eventual consistency is fine for "number of likes on a post." It's dangerous for "user's available credit balance." Know which data requires strong consistency.
  • Use correlation/trace IDs that flow through every service call, log entry, and queue message. Essential for debugging distributed failures.

✓ Strong

"CAP says during a network partition — which will happen — you choose between consistency and availability. For a product catalog, eventual consistency is fine — a price that's 2 seconds stale is acceptable. In practice, most systems are AP because availability is what users experience, but I apply strong consistency selectively where financial correctness matters."

✓ Strong

It's great for social features (likes, feeds), product catalogs, and search indexes. It's dangerous anywhere two operations that depend on the same value must be strongly ordered — financial balances, inventory counts, distributed locks. With eventual consistency, two threads could both read 'balance = $100' and both approve a $90 withdrawal."

Load Balancing

Distributing traffic so no single server drowns while others idle

Core Concept

A load balancer sits in front of your server fleet and distributes incoming requests across multiple backend servers. It simultaneously acts as a traffic router, a health monitor, and a single entry point that hides backend complexity from clients.

Without a load balancer, adding a second server means clients need to know about both — which breaks everything. With one, clients always connect to the same address. When a backend dies, the LB stops sending traffic to it within seconds — automatic failover without code changes.

🎭 Analogy

A load balancer is the host at a restaurant with multiple cashiers. You walk up, they assess which cashier has the shortest queue and direct you there. You don't pick your cashier. If cashier 3 goes on break, the host stops sending people there. When they return, they resume. You, the customer, just see "the restaurant" — the internal routing is invisible to you.

Algorithms Compared

AlgorithmHow it worksBest forWeakness
Round RobinRotate through servers in order: S1, S2, S3, S1...Uniform request cost, same-spec serversIgnores actual server load
Weighted RRS1 gets 3× traffic based on weight configMixed server specs in fleetStill ignores real-time load
Least ConnectionsRoute to server with fewest active connectionsVariable-duration requests (streaming, uploads)Slightly higher overhead to track
IP HashHash client IP → always same serverApps needing session affinityUneven distribution, breaks on server removal

Code Example

NGINXLoad balancer with health checks and weighted routing
upstream api_pool {
  least_conn;

  server api-1:3000 weight=3;    # bigger server gets more traffic
  server api-2:3000 weight=1;
  server api-3:3000 max_fails=3 fail_timeout=30s;

  keepalive 32;  # persistent connections to backends — big perf win
}

server {
  listen 443 ssl;
  server_name api.myapp.com;

  location /api/ {
    proxy_pass http://api_pool;
    proxy_set_header X-Real-IP $remote_addr;        # pass client IP
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header Host $host;
    proxy_http_version 1.1;

    proxy_connect_timeout 5s;
    proxy_read_timeout 30s;

    # Retry on failure for idempotent methods only
    proxy_next_upstream error timeout;
  }
}
Node.jsDeep health check endpoint — what your LB pings
// Shallow: just confirms process is alive
app.get('/health', (req, res) => res.json({ status: 'ok' }));

// Deep: confirms all dependencies are reachable
app.get('/health/deep', async (req, res) => {
  const checks = await Promise.allSettled([
    db.query('SELECT 1'),
    redis.ping(),
  ]);

  const healthy = checks.every(c => c.status === 'fulfilled');

  // 503 → LB removes this server from pool automatically
  res.status(healthy ? 200 : 503).json({
    db: checks[0].status,
    redis: checks[1].status,
  });
});
⚡ Production Tips
  • Avoid sticky sessions (IP hash / cookie affinity). They create hot spots, break during server restarts, and make horizontal scaling painful. Store session in Redis instead — make your app stateless.
  • Health check endpoints must verify actual dependencies (DB, Redis) not just HTTP 200. A server that can't reach the DB shouldn't receive traffic even if its process is running.
  • Set keepalive connections between LB and backends — establishing a new TCP connection for every request adds ~1ms latency at scale.
  • Monitor LB access logs for 502/503 error spikes — they tell you which backend is struggling before your app metrics catch it.
  • AWS ALB + Auto Scaling Group is the managed equivalent of all this NGINX config. Use it — rolling your own is rarely worth the operational burden.
🎯 Interview Prep
"A user logs in fine but gets logged out on the next request. What could cause this?"
✓ Strong

"Classic sticky session problem. The login request hit Server A which stored the session in memory. The next request was load-balanced to Server B which has no knowledge of that session. Fix: externalize session storage to Redis — any server can look up any session. Then you can freely add/remove servers without losing sessions, and sessions survive server restarts."

"What's the difference between L4 and L7 load balancing?"
✓ Strong

"Layer 4 load balances at the TCP/UDP level — routes packets without reading HTTP content. Very fast. Can't route based on URL or headers. Layer 7 reads HTTP — it can route /api/* to API servers and /static/* to a file server, read cookies for affinity, terminate SSL, and make smart routing decisions. AWS ALB and NGINX are L7. Network Load Balancer (NLB) is L4. Most web apps use L7."

Horizontal vs Vertical Scaling

Buy a bigger machine, or buy more machines — and why statelessness is everything

Core Concept

Vertical scaling (scale up): replace your server with a more powerful one — more CPU cores, more RAM, faster disk. Simple. No code changes. But there's a ceiling, and one powerful machine is still a single point of failure.

Horizontal scaling (scale out): add more servers and distribute load across them. Theoretically unlimited. No single point of failure. But it requires your application to be stateless — which is the real engineering challenge that catches most teams off guard.

🎭 Analogy

Vertical scaling is teaching one employee to work faster — there's a human limit. Horizontal scaling is hiring more employees with the same training manual. The challenge isn't hiring — it's making sure any employee can handle any customer, not just "the one who knows where the files are kept." That's statelessness: any server can handle any request at any time.

Making Your App Stateless

Node.jsStateful (won't scale) vs Stateless (will scale)
// ❌ STATEFUL — only works with one server or sticky sessions
const sessions = new Map(); // in-memory — only on THIS process
app.post('/login', (req, res) => {
  const token = generateToken();
  sessions.set(token, { userId: user.id }); // dies on server restart
  res.json({ token });
});
// Also stateful: files saved to /tmp/uploads (not on server 2)
// Also stateful: setInterval() per process (runs N times on N servers)

// ✅ STATELESS — any server can handle any request

// Sessions in Redis — shared across ALL servers
import connectRedis from 'connect-redis';
app.use(session({
  store: new RedisStore({ client: redis }),
  secret: process.env.SESSION_SECRET,
  resave: false
}));

// Files in S3 — readable by any server
app.post('/upload', upload.single('file'), async (req, res) => {
  const url = await s3.upload(req.file); // stored in S3, not local disk
  res.json({ url });
});

// Scheduled jobs via BullMQ — not setInterval() per server
// Caches in Redis — not in-process memory

⚡ Production Tips
  • Vertical scale first when you need a quick fix — it's a 5-minute operation in the cloud. Use horizontal scaling for architectural resilience and sustained growth.
  • The database is the hardest piece to scale horizontally. Start with read replicas for read-heavy apps, then consider sharding only if that's insufficient.
  • Audit your app for statefulness before scaling: local file storage, in-memory sessions, in-process caches, per-process cron jobs. Each one is a blocker.
  • WebSockets require connection affinity. If you use WebSockets + horizontal scaling, use a pub/sub adapter (Socket.io Redis adapter) so messages reach the right server.
  • Auto-scaling: define min/max instance counts and CPU thresholds. Cloud adds/removes instances automatically. You pay only for what you need.
🎯 Interview Prep
"Why is stateless architecture important for horizontal scaling?"
✓ Strong

"Stateless means any server can handle any request without needing context from previous requests. This lets you add servers freely and route any request to any of them. A stateful server (with in-memory session data) requires sticky sessions — all requests from a user must hit the same server. That breaks auto-scaling, creates hot spots, and means rebooting a server loses all its sessions. The fix is moving all state out of the server process: sessions to Redis, files to S3, caches to Redis — then every server is interchangeable."

✓ Strong

"Short-term: vertical scale — upgrade to a larger instance, buys time. Then profile the CPU: is it a hot code path, a slow query, or just pure load? If it's genuine load, make the app stateless and horizontally scale behind a load balancer. If the bottleneck is actually the database (often the real answer on apps that look CPU-bound at the app tier), add read replicas to offload SELECT traffic. I'd also add caching to reduce how often we hit the DB at all."

Database Replication

One writer, many readers — and what to do when the writer dies

Core Concept

Replication continuously copies data from a primary to one or more replicas. This serves two distinct goals: scaling reads (distribute SELECT queries across replicas) and high availability (if the primary dies, promote a replica as the new primary).

The key challenge is replication lag. Most replication is asynchronous — the primary commits a write, then propagates it to replicas. Between those two moments, a replica can return stale data. On a healthy system this lag is sub-millisecond. Under heavy write load it can grow to seconds.

🎭 Analogy

The primary database is the original master copy of a book; replicas are photocopiers continuously making copies. Anyone can read from a copy, but edits only happen on the master. Copies are almost always up-to-date, but there's a brief moment after an edit where they don't have the latest changes — that's replication lag. If the master is destroyed, you promote a copy to be the new master.

Code Example

Node.jsRead/write splitting with replica lag awareness
const primary = new Pool({ host: process.env.DB_PRIMARY });
const replicas = [
  new Pool({ host: process.env.DB_REPLICA1 }),
  new Pool({ host: process.env.DB_REPLICA2 }),
];
let rrIndex = 0;

function getReadPool() {
  return replicas[rrIndex++ % replicas.length]; // round-robin replicas
}

// Writes ALWAYS go to primary
const writeDB = (sql, params) => primary.query(sql, params);

// Reads go to replica by default, primary when consistency needed
const readDB = (sql, params, { usePrimary = false } = {}) =>
  (usePrimary ? primary : getReadPool()).query(sql, params);

// "Read your own writes" — read from primary right after writing
app.put('/profile', async (req, res) => {
  await writeDB('UPDATE users SET name=$1 WHERE id=$2', [req.body.name, req.user.id]);

  // Read from primary — replica may not have the update yet
  const user = await readDB(
    'SELECT * FROM users WHERE id=$1', [req.user.id],
    { usePrimary: true } // ← bypass replica lag for this response
  );
  res.json(user);
});
SQLMonitor replication lag in PostgreSQL
-- On primary: see lag for each connected replica
SELECT
  client_addr,
  state,
  write_lag,
  replay_lag,
  (sent_lsn - replay_lsn) AS lag_bytes
FROM pg_stat_replication;

-- On replica: how far behind is THIS replica?
SELECT now() - pg_last_xact_replay_timestamp() AS replication_delay;

-- Alert if replication_delay > 5 seconds in production

Async vs Sync Replication

Async (Default)

Primary commits, then sends changes. Fast writes. Risk: data loss if primary crashes before replicating. Most common.

Synchronous

Primary waits for replica to confirm before committing. Zero data loss. Slower writes — every write waits for a network round-trip to the replica.

Semi-Sync

Wait for N of M replicas to ack. Balance of safety and speed. Postgres supports this via synchronous_standby_names.

Failover

Primary dies → promote replica. Managed DBs (RDS Multi-AZ) do this automatically in 20–60 seconds.

⚡ Production Tips
  • Monitor replication lag in dashboards. Alert at >100ms. Lag >1s means the replica is falling behind under write load — investigate immediately.
  • The "read your own writes" problem is the #1 UX bug caused by read replicas. After a user makes a change, route that user's next read to the primary for at least one request.
  • Use managed database services (AWS RDS, Cloud SQL, Supabase) — they handle replication, monitoring, and automated failover. Only self-manage if cost justifies it at massive scale.
  • Failover time for managed DBs is 20–60 seconds. Your app must handle temporary DB unavailability with retries and circuit breakers — not crash.
  • Replicas can serve different roles: one for application read traffic, one for analytics (expensive queries won't affect prod), one as a warm standby for failover.
🎯 Interview Prep
"A user updates their username. When they refresh the page, they see the old one. Why?"
✓ Strong

"Classic replication lag bug. The write went to the primary, but the page reload read from a replica that hasn't received the update yet. The fix is 'read your own writes' consistency — after any write, route that user's next read to the primary for one request cycle. Alternatively, use a short version cookie: after a write, set a cookie that tells the app to read from primary for the next 1–2 seconds, then switch back to replicas."

"How does database failover work in a managed setup?"
✓ Strong

"In AWS RDS Multi-AZ, there's a synchronous standby replica in a different availability zone. When the primary fails, AWS automatically promotes the standby and updates the DNS CNAME that our app uses to connect. This takes 20–60 seconds during which the DB is unreachable. My app handles this with connection retries and circuit breakers — the brief outage is logged and alerts fire, but the app recovers automatically once the new primary is up."

Quick Reference

ReplicaRead-only copy. Replicates from primary. Can have many.
Async replicationFast writes. Possible data loss on crash. Default in most systems.
Sync replicationZero data loss. Slower — waits for replica ack on every write.

Sharding / Partitioning

When one database — even with replicas — can't hold all your data

Core Concept

Sharding splits your data across multiple database instances called shards. Each shard holds a subset of rows. A shard key determines which shard any given row lives on. This lets your database tier scale horizontally — but at an enormous complexity cost.

Sharding is a last resort. Exhaust every other option first: better indexing, caching, read replicas, query optimization, vertical scaling. Only shard when you've genuinely hit the limits of a single node. Most apps never need to. The ones that do (Facebook, Twitter, Uber) have dedicated database teams to manage it.

🎭 Analogy

A phone directory that's grown too large for one book. You split it: A–M in one volume, N–Z in another. To find "Alice Smith" you go to the A–M book. To compare Alice and Zoe, you need both books. That's the cross-shard query problem — anything requiring data from multiple shards needs to be coordinated at the application level, since the database can't JOIN across shard boundaries.

Sharding Strategies

Hash Sharding

shard = hash(id) % N. Even distribution. No range queries. Adding shards requires consistent hashing to avoid re-migrating all data.

Range Sharding

id 1–1M → shard A, 1M–2M → shard B. Range queries are efficient. Risk of hotspots — new users always hit the newest shard.

Directory Sharding

Lookup table: user 123 → shard C. Flexible, rebalanceable. The lookup table itself is a bottleneck and single point of failure.

Geo Sharding

US users → US shard, EU users → EU shard. Reduces latency, satisfies data residency laws (GDPR). Complex for users who travel.

Code Example

Node.jsApplication-level shard routing
const SHARD_COUNT = 4;
const shards = [
  new Pool({ host: 'shard-0.db' }),
  new Pool({ host: 'shard-1.db' }),
  new Pool({ host: 'shard-2.db' }),
  new Pool({ host: 'shard-3.db' }),
];

const getShard = (userId) => shards[userId % SHARD_COUNT];

// Single user lookup — fast, hits only one shard
async function getUser(userId) {
  return getShard(userId).query('SELECT * FROM users WHERE id=$1', [userId]);
}

// Cross-shard query — expensive, must fan out to all shards
// AVOID WHERE POSSIBLE. Use secondary indexes in Redis instead.
async function findByEmail(email) {
  const results = await Promise.all(
    shards.map(pool => pool.query('SELECT * FROM users WHERE email=$1', [email]))
  );
  return results.flatMap(r => r.rows)[0] || null;
}

// Better: maintain a secondary index in Redis
// On user creation: redis.set(`email:${email}`, userId)
async function findByEmailFast(email) {
  const userId = await redis.get(`email:${email}`);
  if (!userId) return null;
  return getUser(parseInt(userId)); // → routed to correct shard
}
⚡ Production Tips
  • Choose your shard key carefully and never change it. Re-sharding is one of the most painful migrations possible — you're essentially moving every row in your database.
  • Best shard key: high cardinality, evenly distributed, present in most queries. user_id is usually good. created_at is bad (new shard always gets all new writes).
  • Cross-shard JOINs are not possible in SQL. Design your schema so entities queried together live on the same shard — shard orders on user_id so a user's orders co-locate with their profile.
  • Consider managed sharding: Vitess (MySQL), Citus (Postgres), CockroachDB, PlanetScale. These abstract much of the routing and migration complexity.
  • Maintain secondary indexes (Redis or Elasticsearch) for attributes you need to query across shards — email, phone, username — to avoid expensive fan-out queries.
🎯 Interview Prep
"How would you shard a users table with 1 billion rows?"
✓ Strong

"First I'd verify sharding is actually necessary — maybe read replicas and vertical scale are sufficient. If not, I'd use hash sharding on user_id with consistent hashing, so adding shards later only migrates ~1/N of data instead of everything. I'd keep a secondary index in Redis for email-based lookups to avoid fan-out queries. I'd also co-shard the orders table on user_id, so a user's profile and orders live on the same shard and I can still JOIN them locally."

Optimistic Locking

Assume the best, verify on commit, retry on conflict

Core Concept

Optimistic locking avoids holding database locks during the read-modify-write cycle. Instead of locking a row when you read it, you optimistically assume no conflict will happen. When you write back, you include a version guard in the WHERE clause. If someone else modified the row between your read and write, the guard fails — 0 rows updated — and you retry with a fresh read.

The opposite, pessimistic locking (SELECT FOR UPDATE), locks the row on read and blocks all other writers until you commit. Safe but creates contention under load. Optimistic locking has zero blocking — at the cost of possible retries when conflicts occur.

🎭 Analogy

Editing a Wikipedia article. You open the page (read without lock), make edits, click Save. Wikipedia checks: has anyone else edited this since you opened it? If yes — conflict, merge required. If no — your edit goes through. No one is blocked from reading while you edit. Conflicts are detected on save. That's optimistic locking.

Code Example

SQL + Node.jsOptimistic lock with version column and retry loop
-- Schema: version column incremented on every write
ALTER TABLE products ADD COLUMN version INT NOT NULL DEFAULT 1;

-- UPDATE includes version guard — only succeeds if no concurrent write
UPDATE products
  SET stock = stock - $1, version = version + 1, updated_at = now()
  WHERE id = $2 AND version = $3;   -- ← the guard
-- rowCount=1 → success. rowCount=0 → conflict, retry.
Node.jsFull retry loop with exponential backoff
async function deductStock(productId, quantity, maxRetries = 5) {
  for (let attempt = 0; attempt < maxRetries; attempt++) {

    // 1. Read current state (including version)
    const { rows: [p] } = await db.query(
      'SELECT id, stock, version FROM products WHERE id=$1', [productId]
    );

    if (!p) throw new Error('Product not found');
    if (p.stock < quantity) throw new Error('Insufficient stock');

    // 2. Conditional write — WHERE version = old_version
    const result = await db.query(`
      UPDATE products SET stock = stock - $1, version = version + 1
      WHERE id = $2 AND version = $3
    `, [quantity, productId, p.version]);

    if (result.rowCount === 1) {
      return { success: true, newStock: p.stock - quantity };
    }

    // 3. Version mismatch — concurrent write won. Wait and retry.
    const delay = 10 * Math.pow(2, attempt) + Math.random() * 10;
    await new Promise(r => setTimeout(r, delay));
  }
  throw new Error(`Conflict after ${maxRetries} attempts`);
}

// REST API pattern: ETags + If-Match headers
// GET /products/42 → ETag: "v5"
// PUT /products/42 If-Match: "v5" → 412 Precondition Failed if version changed
app.put('/products/:id', async (req, res) => {
  const version = parseInt(req.headers['if-match']);
  if (!version) return res.status(428).json({ error: 'If-Match required' });

  const result = await db.query(`
    UPDATE products SET price=$1, version=version+1 WHERE id=$2 AND version=$3
  `, [req.body.price, req.params.id, version]);

  if (result.rowCount === 0) {
    return res.status(412).json({ error: 'Resource was modified by another client' });
  }
  res.json({ success: true });
});
⚡ Production Tips
  • Use optimistic for low-contention scenarios: profile edits, CMS updates, config changes. Use pessimistic (SELECT FOR UPDATE) for high-contention: inventory flash sales, wallet balances.
  • Under very high contention, optimistic locking degrades to a spin-wait. If conflict rate exceeds ~20%, switch to pessimistic — the lock overhead is cheaper than constant retries.
  • ORMs like Sequelize and TypeORM support optimistic locking natively via @Version() decorators. Use them rather than hand-rolling.
  • Track conflict rate as a metric. A spike indicates a hot row or a bug causing write storms — both need investigation.

Event-Driven Architecture

Services that react to what happened, not to direct commands

Core Concept

In a traditional architecture, Service A calls Service B directly: emailService.sendWelcome(user). This creates tight coupling — A knows about B, A breaks if B is slow or down, and every new requirement means changing A.

In event-driven architecture, A emits an event: user.registered. Any interested service subscribes and reacts independently. A doesn't know who's listening. Adding a new consumer requires zero changes to the publisher. This is the deepest form of decoupling.

🎭 Analogy

A newspaper vs phone calls. If a news agency called every subscriber individually to report each story, they'd be tightly coupled and impossibly slow. Instead, they publish a newspaper — whoever is interested reads it and reacts. New subscribers just add their address. The agency never changes its process. That's event-driven: publish once, multiple independent consumers react at their own pace.

Code Example

// ORDER SERVICE — emits event, knows NOTHING about downstream

  const order = await db.insert('orders', orderData);

  });

⚡ Production Tips

Circuit Breakers

Stop hammering a failing service — fail fast, degrade gracefully

Core Concept

When Service B is failing, Service A shouldn't keep sending requests to it. Each failed request might wait 30 seconds before timing out — holding a thread and connection for 30 seconds. Under load, A's thread pool fills up waiting for B. Then A starts failing too. The failure propagates. That's a cascading failure, and it's how one misbehaving microservice brings down the entire system.

A circuit breaker monitors failure rate and "trips" when it exceeds a threshold. While open, calls fail immediately with an error or fallback — no thread held, no timeout waited. After a cooldown, one test request probes whether B has recovered.

🎭 Analogy

An electrical circuit breaker in your home. When there's a fault, it trips — breaking the circuit instantly instead of letting wires overheat and cause a fire. You don't keep running appliances while it's tripped. You wait, fix the issue, then reset the breaker. Software circuit breakers are identical: trip on failure threshold, stop sending requests, test after cooldown, reset when healthy.

Three States

🟢 Closed

Normal operation. Requests pass through to downstream. Failure counter tracked in a rolling window.

🔴 Open

Threshold breached. All calls fail immediately with error or fallback. Downstream gets zero traffic.

🟡 Half-Open

Cooldown expired. One probe request allowed. Success → Closed. Failure → back to Open.

Code Example

Node.jsCircuit breaker with opossum + fallback + observability
import CircuitBreaker from 'opossum';

async function callPaymentService(payload) {
  const response = await fetch('https://payment.internal/charge', {
    method: 'POST',
    body: JSON.stringify(payload),
    signal: AbortSignal.timeout(3000)
  });
  if (!response.ok) throw new Error(`Payment error: ${response.status}`);
  return response.json();

const breaker = new CircuitBreaker(callPaymentService, {
  timeout: 3000,                  // trip if takes > 3s
  errorThresholdPercentage: 50,   // trip if 50%+ calls fail
  resetTimeout: 30000,            // try again after 30s
  volumeThreshold: 10,            // min 10 calls before can trip (avoids startup noise)
  rollingCountTimeout: 10000,     // measure failure rate over last 10s
});

// Fallback: graceful degradation when circuit is Open
breaker.fallback((payload, err) => ({
  status: 'queued',
  message: 'Payment is being processed. You will receive an email confirmation.',
  retryAfter: 30
}));

// Observability — instrument state changes as metrics

  metrics.increment('circuit_breaker.payment.open');
  logger.error('⚡ Payment circuit OPEN — service unavailable');
});

breaker.on('close', () => logger.info('✅ Payment circuit CLOSED — service recovered'));

// Usage

// If circuit is open: returns the fallback object immediately
// If circuit is closed: calls payment service normally
⚡ Production Tips
  • Every external service call should have a circuit breaker — payments, emails, third-party APIs, internal microservices. All of them can fail.
  • Design a meaningful fallback for every circuit. Don't just return an error — return a degraded experience: queue the payment, show cached data, disable the feature gracefully.
  • Instrument circuit state changes as metrics. Monitor circuit.open events in your dashboards — they're an early warning that a dependency is struggling.
  • Set volumeThreshold to prevent tripping on startup when only 1–2 requests have been made — a single failure shouldn't open the circuit.
  • Combine with retries: retries handle transient failures on a healthy service; circuit breakers handle sustained outages. They're complementary, not alternatives.

Retry Strategies

Retry smarter — exponential backoff, jitter, and knowing when NOT to retry

Core Concept

Transient failures are normal in distributed systems — a network blip, a server restart, a brief overload. The naive response is to retry immediately. The problem: if a service is overloaded and 1,000 clients all retry every 100ms, you've created a thundering herd — you're DDoSing the already-struggling service with retry traffic.

The production solution is exponential backoff with jitter: each retry waits longer than the last (exponential), with random variance (jitter) to spread retries across time and prevent synchronized retry storms.

🎭 Analogy

You're calling a friend whose phone is busy. Option A (bad): call back every second. Option B (backoff): wait 1s, 2s, 4s, 8s. Better. But if 500 people are doing the same thing, they all retry at exactly t=2s, t=4s — synchronized surges. Option C (backoff + jitter): wait 1s ±0.3s, 2s ±0.6s. Everyone retries at slightly different times, spreading load. The service gets breathing room between each wave.

Code Example

Node.jsProduction-grade retry with backoff, jitter, and error discrimination
async function withRetry(fn, options = {}) {
  const {
    maxAttempts = 5,
    baseDelay = 1000,     // 1 second
    maxDelay = 30000,     // cap at 30 seconds
    jitterFactor = 0.3,  // ±30% randomness
    onRetry = null
  } = options;

  let lastError;

  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    try {
      return await fn(attempt);
    } catch (err) {
      lastError = err;

      // NEVER retry client errors — they won't succeed on retry
      if (err.status && err.status >= 400 && err.status < 500) throw err;

      if (attempt === maxAttempts) break;

      // Exponential: 1s, 2s, 4s, 8s, 16s — capped at 30s
      const exponential = Math.min(baseDelay * Math.pow(2, attempt - 1), maxDelay);
      // Jitter: ±30% — breaks synchronization across many retrying clients
      const jitter = exponential * jitterFactor * (Math.random() * 2 - 1);
      const delay = Math.max(0, exponential + jitter);

      onRetry?.({ attempt, delay, error: err.message });
      await new Promise(r => setTimeout(r, delay));
    }
  }

  throw new Error(`Failed after ${maxAttempts} attempts: ${lastError?.message}`);
}

// Usage: payment with retry
const result = await withRetry(
  async (attempt) => callPaymentAPI(payload),
  {
    maxAttempts: 4,
    baseDelay: 500,
    onRetry: ({ attempt, delay }) =>
      logger.warn(`Payment retry ${attempt}, waiting ${Math.round(delay)}ms`)
  }
);

// Attempt 2: ~500ms, Attempt 3: ~1s, Attempt 4: ~2s
⚡ Production Tips
  • Only retry on transient errors: network errors (ECONNRESET, ETIMEDOUT), 429 Too Many Requests (respect the Retry-After header), 503 Service Unavailable. Never retry 4xx — they represent bad requests that won't succeed on retry.
  • Retries require idempotency. Retrying a POST that creates an order can create duplicates. Always use idempotency keys on mutation endpoints that will be retried.
  • Respect Retry-After headers from 429 responses — the server knows the correct backoff window, don't override it with your own.
  • In a microservices system, consider a retry budget: cap retries at 10% of total outgoing requests. This prevents retry amplification during cascading failures.
  • Log every retry attempt with attempt number and delay. These logs are invaluable for diagnosing which dependencies are flaky in production.

Observability

If you can't see it, you can't fix it — logs, metrics, and traces

Core Concept

Observability is your ability to understand what's happening inside your system by looking at its external outputs. Monitoring tells you when something is wrong. Observability tells you why. The difference is critical at 2am when an alert fires and you need to diagnose a problem you've never seen before — without adding new instrumentation first.

Three pillars: Logs tell you what happened (narrative). Metrics tell you how the system is performing (numbers over time). Traces show you how a single request flowed through every service (the journey map).

🎭 Analogy

Observability is the cockpit instruments. Logs are the flight recorder — detailed record of every event. Metrics are the gauges (altitude, speed, fuel) — real-time numbers you glance at continuously. Traces are the flight path — which route did this request take through your microservices? When you have all three, you can diagnose any problem. Flying blind means you only know there's a crash when users tweet about it.

"It works on my machine" — and now it works everywhere

Core Concept

The operating system for your distributed application

Core Concept

Kubernetes (K8s) manages containers across a cluster of machines. You declare desired state — "run 3 replicas of this API" — and K8s continuously works to achieve and maintain it. Containers crash? The paradigm shift: you stop thinking about servers and start thinking about desired state and resources. You don't deploy by SSHing into machines — you update a YAML manifest and Kubernetes figures out how to make it so.

🎭 Analogy

Kubernetes is an operations manager for a fleet of servers. You say "I want 5 copies of the API service running, with at least 512MB RAM each, spread across different buildings." The manager schedules workers (pods), replaces any who stop showing up (restarts crashed containers), moves them to healthier buildings (reschedules from failed nodes), and hires more or lays off based on demand (auto-scaling). You never talk to individual workers — only to the manager.

⚡ Production Tips
  • Always set resource requests AND limits. Without requests, the scheduler places pods randomly. Without limits, one runaway pod OOMs an entire node, killing all other pods on it.
  • Readiness probe: controls traffic routing — failing = removed from Service endpoints. For slow startups. Liveness probe: controls pod lifecycle — failing = pod killed and restarted. For deadlock detection. Wrong choice = chaos.
  • Never use :latest tag in production. Always pin to a specific version or Git SHA — predictable, rollback-able.
  • Use kubectl rollout undo deployment/api to instantly roll back a bad deploy. This only works reliably with pinned image versions.
  • Store secrets in an external manager (AWS Secrets Manager, HashiCorp Vault) and sync to K8s Secrets via the External Secrets Operator — base64 in a YAML file is not encryption.

"What's the difference between a readiness probe and a liveness probe?"
✓ Strong

"Different purposes. Readiness controls traffic routing — when a pod's readiness probe fails, K8s removes it from the Service's endpoint list, stopping new requests to it. Used for pods not yet ready to serve traffic (still warming up, loading caches). Liveness controls pod lifecycle — when it fails, K8s kills and restarts the pod. Used for pods that are stuck or deadlocked and would never recover on their own. Mixing them up causes either unnecessary restarts or dead pods receiving live traffic."

"How does a rolling deployment work?"
✓ Strong

"With RollingUpdate, K8s starts a new pod with the new image, waits for its readiness probe to pass, then terminates one old pod. At every point during rollout, live pods serve traffic — zero downtime. The readiness probe is critical: without it, K8s sends traffic to pods that haven't finished starting."

CI/CD

Every commit deployable — automating the path from code to production

Core Concept

Continuous Integration (CI): Every push automatically triggers a pipeline — build, lint, test. If any step fails, the PR is blocked. The goal: catch bugs at the moment of introduction, not days later when someone else encounters them.

Continuous Deployment (CD): Every commit that passes CI on the main branch is automatically deployed to production. No manual deploy steps. Deployments become so routine and automated that they're boring. The more frequent, the smaller each change, the lower the risk per deploy.

🎭 Analogy

CI/CD is a car assembly line with quality gates. Every car (commit) passes through: paint (lint), then engine test (unit tests), then full inspection (integration tests). A car failing any gate stops the line — it doesn't proceed to delivery. A car passing all gates ships automatically. You never manually inspect individual cars — the process itself guarantees quality.

Reverse Proxy

The traffic cop, SSL terminator, and security shield in front of your servers

Core Concept

A reverse proxy sits between the internet and your backend servers. Clients always connect to the proxy — your actual servers are never directly exposed. The proxy handles SSL termination, request routing, compression, static file serving, and rate limiting — offloading all of this from your application code so it can focus on business logic.

Forward proxy (different thing): client-side, anonymizes client requests. Reverse proxy: server-side, protects and optimizes backend services. NGINX, Caddy, Traefik, HAProxy are the common choices.

🎭 Analogy

A reverse proxy is a hotel's front desk. Every guest (request) goes through the front desk — they never wander into the kitchen or staff areas (backend servers). The front desk checks IDs (auth headers), enforces limits (rate limiting), directs people to the right department (routing), and handles general services (compression, SSL, static files). The hotel's actual operations happen behind the desk, protected from direct public access.

Code Example

limit_req_zone $binary_remote_addr zone=login:10m rate=1r/s;  # strict for auth

  least_conn;

  add_header X-Frame-Options DENY;

  gzip on;

  gzip_min_length 1000;

  # API traffic → Node.js backends
  location /api/ {
    limit_req zone=api burst=20 nodelay;

    proxy_pass http://api_pool;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;         # pass original client IP
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    proxy_connect_timeout 5s;
    proxy_read_timeout 30s;
    proxy_next_upstream error timeout;
  }

  # Auth endpoints — strict rate limit (brute force protection)
  location /api/auth/ {
    limit_req zone=login burst=5;
    proxy_pass http://api_pool;
  }

  # Static assets — served directly from disk, max caching
  location /static/ {
    root /var/www;
    expires 1y;
    add_header Cache-Control "public, immutable";
    access_log off;
  }

  # Block common scanner paths
  location ~ /(wp-admin|phpMyAdmin|.env) { return 404; }
}

SSL Termination

SSL/TLS is computationally expensive — handshakes, certificate verification, encryption. SSL termination at the proxy means: the proxy handles the HTTPS connection from clients, then forwards requests to backends over plain HTTP on the internal (trusted) network. Your Node.js servers don't deal with TLS at all — simpler and faster.

This is safe when your internal network is a trusted VPC or private network. The alternative (re-encrypting from proxy to backend via mTLS) adds complexity most apps don't need unless you have strict compliance requirements.

⚡ Production Tips
  • Set proxy_set_header X-Real-IP $remote_addr — without this, your app sees all requests as coming from the proxy (127.0.0.1), making IP-based rate limiting and geo-detection useless.
  • Use Caddy if you want automatic HTTPS — it provisions and renews Let's Encrypt certificates automatically. NGINX requires certbot separately.
  • Serve static assets (JS, CSS, images) directly from NGINX — it's 10–50× faster than proxying to Node.js. Put a CDN (CloudFront, Fastly) in front for global distribution.
  • Set Strict-Transport-Security (HSTS) — tells browsers to always use HTTPS for your domain, even if the user types http://.
  • In cloud environments, use a managed load balancer (AWS ALB, GCP CLB) instead of maintaining NGINX — they handle scaling, health checks, SSL certs, and DDoS protection automatically.

API Design

APIs are forever — design them like you'll be stuck with them

Core Concept

APIs are contracts between your service and its consumers. Once published, they're extremely hard to change — clients depend on the exact URL structure, response shapes, and behavior you defined. A bad field name in v1 will haunt you for years. Design thoughtfully upfront, because the cost of fixing a bad API is proportional to the number of clients that have integrated with it.

Good API design is about three things: predictability (behaves as expected, follows conventions), consistency (similar operations look and behave similarly), and evolvability (you can add features without breaking existing clients).

🎭 Analogy

Designing an API is like laying a city's streets. Once streets are paved and buildings built around them, moving a street is enormously expensive — too many addresses depend on it. You can add new roads but can't easily rename or remove old ones. Get the foundational grid right before building, because you'll live with these decisions for decades. Versioning is your escape hatch when you absolutely must move a street.

Code Examples

// Consistent error shape — every error looks the same across the API
class ApiError extends Error {
  constructor(statusCode, code, message, details = null) {
    super(message);
    this.statusCode = statusCode;
    this.code = code;       // machine-readable: 'INSUFFICIENT_FUNDS'
    this.details = details; // validation errors, extra context
  }
}

// Global error handler — uniform output regardless of where error originated
app.use((err, req, res, next) => {
  if (err instanceof ApiError) {
    return res.status(err.statusCode).json({
      error: { code: err.code, message: err.message, details: err.details, traceId: req.traceId }
    });
  }
  res.status(500).json({ error: { code: 'INTERNAL_ERROR', message: 'Something went wrong' } });
});

// Cursor-based pagination — stable, O(log n), scales to billions of rows
app.get('/v1/orders', authenticate, async (req, res) => {
  const limit = Math.min(parseInt(req.query.limit) || 20, 100); // cap max page size
  const cursor = req.query.cursor ? parseInt(req.query.cursor) : 0;

  // Fetch one extra row to check if there's a next page
  const rows = await db.query(`
    SELECT * FROM orders WHERE user_id = $1 AND id > $2
    ORDER BY id ASC LIMIT $3
  `, [req.user.id, cursor, limit + 1]);

  const hasMore = rows.length > limit;
  const data = hasMore ? rows.slice(0, limit) : rows;

  res.json({
    data,
    pagination: {
      hasMore,
      nextCursor: hasMore ? data[data.length - 1].id : null,
      count: data.length
    }
  });
});

HTTP, TCP, DNS, and the Request Lifecycle

What really happens after a user presses Enter

Core Concept

A backend engineer should understand the full request path: browser checks cache, resolves DNS, opens a TCP connection, negotiates TLS, sends HTTP, passes through CDN/proxy/load balancer, reaches the app, queries dependencies, and returns a response. Production bugs often hide in the spaces between these layers.

DNS

Maps name to IP. TTL controls how long resolvers cache answers. Low TTL helps failover but increases lookup traffic.

TCP

Reliable ordered byte stream. Handshake, congestion control, retransmits, connection reuse, and head-of-line blocking matter for latency.

HTTP/1.1

Text protocol, keep-alive, one in-flight response per connection unless pipelining. Simple and common.

HTTP/2

Multiplexes streams over one TCP connection. Reduces connection count, but TCP packet loss can still affect all streams.

HTTP/3

Runs over QUIC/UDP. Faster connection setup and better behavior under packet loss for modern clients.

The app authenticates, validates, queries DB/cache/queues, returns a status code and response headers. I would mention timeouts, connection reuse, cache headers, trace IDs, and where failures can happen."

Schema Migrations and Backward Compatibility

Change databases without breaking running code

Expand / Contract

Production deploys are not instantaneous. Old and new app versions may run at the same time, workers may lag, and replicas may apply changes later. Safe migrations are backward compatible: expand the schema first, deploy code that can read/write both shapes, backfill, then contract the old column later.

Migration PatternRename column without downtime
-- Bad: ALTER TABLE users RENAME COLUMN name TO full_name; old app breaks immediately

-- 1. Expand
ALTER TABLE users ADD COLUMN full_name text;

-- 2. Dual write in app: write both name and full_name
-- 3. Backfill in small batches, not one huge lock-heavy update
WITH batch AS (
  SELECT id FROM users WHERE full_name IS NULL ORDER BY id LIMIT 1000
)
UPDATE users
SET full_name = users.name
FROM batch
WHERE users.id = batch.id;

-- 4. Switch reads to full_name after backfill is complete
-- 5. Contract in later deploy
ALTER TABLE users DROP COLUMN name;

Connection Pools, Timeouts, and Backpressure

Most outages are resource exhaustion wearing a disguise

Core Concept

A connection pool limits how many concurrent connections your app opens to a dependency. Too small and requests queue inside your app. Too large and you overload the database. Senior engineers size pools deliberately and add backpressure so failure is controlled instead of cascading.

Pool Size

Total app instances times pool size must fit within the DB max connections, with room for migrations and admin access.

Queue Timeout

If a request waits too long for a connection, fail fast. Do not allow unlimited in-process queues.

Request Deadline

Carry a deadline through all downstream calls. Stop doing work after the client has gone away.

Backpressure

Reject or shed load when saturated. Better a fast 503 than a slow global outage.

Interview Prep

Strong

"Each pod probably opened its own pool. Ten pods with pool size 30 means 300 DB connections. More connections do not mean more throughput once the DB is CPU/IO bound; they add context switching and lock contention. I would cap total connections, use PgBouncer if needed, tune pool size from observed latency, and add queue timeouts/backpressure."

ORMs, N+1 Queries, and Data Access Boundaries

Convenience is good until it hides the query plan

Core Concept

ORMs speed up development but can hide expensive query patterns. The classic N+1 bug loads a list, then queries related data one row at a time. Ten rows look fine. Ten thousand rows melt the database.

PatternN+1 query and fix

for (const order of orders) {
  order.customer = await Customer.findByPk(order.customerId);

// Better: eager load or join in one bounded query
const orders = await Order.findAll({
  include: [{ model: Customer, attributes: ['id', 'name'] }],

  • Put hard limits on list endpoints. Unbounded ORM queries become accidental table scans.

Outbox Pattern, Sagas, and Distributed Transactions

When one local transaction is not enough

Core Concept

Databases and message brokers do not automatically commit together. If you save an order then fail before publishing OrderCreated, downstream systems never hear about it. If you publish first then DB commit fails, consumers react to an order that does not exist. The outbox pattern fixes this by writing business data and an event record in the same database transaction.

SQLTransactional outbox

Testing Strategy for Backend Systems

Confidence comes from the right tests at the right boundary

Test Pyramid in Practice

Good backend testing is not "unit tests everywhere." It is a layered strategy: unit tests for pure logic, integration tests for database and queues, contract tests between services, end-to-end tests for a few critical flows, and load tests for capacity assumptions.

Unit

Fast tests for business logic, validators, mappers, and policy decisions. No network or real DB.

Integration

Use real Postgres/Redis when behavior matters: transactions, indexes, constraints, locks.

Contract

Producer and consumer agree on API/event shape. Prevents independent service deploys from breaking clients.

E2E

Few, high-value tests for login, checkout, payment, webhook, and recovery flows.

Load

Validates p95/p99 latency, pool sizes, queue throughput, and database saturation points.

"Unit test validation and amount calculations, integration test idempotency and transaction behavior with a real DB, mock the payment provider with contract expectations, test webhook replay/dedup, and add concurrency tests so two requests with the same idempotency key cannot double-charge. Do not put durable user data on app server disk

Core Concept

App containers are disposable. User uploads belong in object storage such as S3/GCS/Azure Blob, metadata belongs in the database, and search belongs in a search engine when relational indexes are no longer enough. Externalized state is what lets your app scale horizontally.

Universal Production Anti-Patterns

🚫 Never Do These in Production
  • Never do network calls (HTTP, SMTP, external APIs) inside a DB transaction — holding a lock while waiting for a network timeout is catastrophic for throughput.
  • Never retry 4xx errors — they're client errors that won't succeed on retry. You'll just spam the service with guaranteed failures.
  • Never store sessions or file uploads on local server disk — breaks horizontal scaling immediately and silently.
  • Never use :latest Docker image in production — non-deterministic, impossible to reliably roll back, can change without warning.
  • Never cache mutable data without a clear invalidation strategy — cache inconsistency bugs are the hardest to debug and reproduce in production.
  • Never log sensitive data (passwords, API keys, credit card numbers, full JWTs) — logs are often stored in plaintext and shared with third-party monitoring services.
  • Never ignore replication lag — the "read your own writes" bug is a real UX disaster that's easy to miss in single-server development.
  • Never skip resource limits in Kubernetes — one OOM pod can kill an entire node and all neighboring pods, causing a cascading outage.
