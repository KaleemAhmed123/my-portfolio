Execution

The Process Model

How code actually runs.

Process vs Thread

A **process** is an isolated instance of a running program with its own memory space (heap). A **thread** is a unit of execution within a process; threads share the process's memory space but have their own stack.

Fork & Exec

fork() creates an exact duplicate of the current process (child). exec() replaces the current process image with a new program. This is how shells run commands.

Signals

Software interrupts sent to a process.
SIGTERM (15): Graceful shutdown request.
SIGKILL (9): Immediate forced termination (cannot be caught).
SIGHUP (1): Hangup, often used to tell daemons to reload config.

Zombies & Orphans

Zombie: A process that has finished executing but its parent hasn't read its exit status yet.
Orphan: A process whose parent has died; adopted by init (PID 1).

Resources

Memory Management

Where the data lives.

Virtual Memory & Paging

The OS gives each process the illusion of a large, contiguous memory space. Virtual addresses are mapped to physical RAM via page tables. If physical RAM is full, pages are swapped to disk (Swap space), causing massive performance drops.

Stack vs Heap

Stack: Fast, LIFO memory for local variables and function calls. Managed automatically. Size is fixed.
Heap: Dynamic memory for objects and closures. Managed by Garbage Collection (in JS/Java) or manually (C/C++). Memory leaks happen here.

03
Storage

File System

Why "everything is a file" is a design decision and not a slogan.

The claim people repeat is that on Unix everything is a file. The useful version is more precise: everything is reachable through the same small set of operations — open, read, write, close. A regular file, a pipe, a terminal, a socket, and a kernel counter in /proc are wildly different things underneath, and they all answer to the same four calls. That is why shell pipelines compose so well, and why a program that reads a file needs no changes to read from a socket instead.

Inodes: names are not files

This is the idea that makes the rest of the section fall into place. A file's data and metadata — size, permissions, owner, timestamps, and the pointers to its data blocks — live in a structure called an inode, identified by a number. The filename is not part of it. A directory is just a table mapping names to inode numbers.

So a filename is a reference to an inode, and an inode counts how many references point at it. Several consequences that look surprising until you know this:

Hard links

A second name pointing at the same inode. Not a copy and not a shortcut — genuinely the same file with two names, and neither is the "real" one. Delete either name and the data survives, because the link count is still above zero.

Symbolic links

A small file whose contents are a path. Resolved at access time, so it can point across filesystems and can dangle if the target is removed. A hard link cannot dangle; a symlink is the one that can break.

Deleting is unlinking

rm removes a name and decrements the count. Space is reclaimed when the count reaches zero and no process still holds the file open — which is why deleting a log file does not free the disk until you restart the process writing to it.

Renames are cheap

mv within a filesystem rewrites a directory entry and touches no data, however large the file. Across filesystems it becomes a real copy plus a delete, which is why one is instant and the other is not.

"No space left on device" with free space showing

A filesystem has a finite number of inodes, allocated when it is created, separate from its data capacity. Millions of tiny files — cache entries, session files — can exhaust the inode table while df -h still reports free gigabytes. df -i shows the inode usage, and it is the check that explains an otherwise baffling outage.

File descriptors

When a process opens something, the kernel returns a small integer: an index into that process's table of open files. 0, 1, and 2 are standard input, output, and error, which is what makes redirection work — 2>&1 simply points descriptor 2 at whatever descriptor 1 currently refers to.

Descriptors are a per-process limited resource (ulimit -n), and because sockets are also descriptors, a server that leaks connections eventually fails with EMFILE: too many open files. That error usually means a leak — connections or file handles opened in a loop and never closed — rather than a limit that is genuinely too low. Raise the limit only after you have checked which it is.

Permissions

Three classes — owner, group, other — each with read, write, execute. The octal notation is just those three bits per class: r=4, w=2, x=1, so 644 is owner read-write, everyone else read-only, and 755 adds execute.

The part worth knowing beyond the arithmetic is that on a directory the bits mean something different: r lets you list the names, w lets you create and delete entries in it, and x lets you traverse into it and access things by full path. This is why you can sometimes read a file whose directory you cannot list, and why removing a file needs write permission on the directory rather than on the file.

The page cache

Reads and writes do not usually go straight to disk. The kernel keeps recently used file pages in memory, serves repeat reads from there, and buffers writes to flush later. This is why the second run of a command is dramatically faster, and why free -h showing very little "free" memory is normal and healthy — cache is memory doing useful work, and it is released the moment a process needs it. The tradeoff is durability: a write that has returned successfully may still only be in the cache, which is what fsync is for and why databases call it explicitly at commit.

Analogy

The inode is the storage unit; the filename is a label on a keyring. Hard links are two labels on the same unit — remove one and the unit stays. A symlink is a note saying "see unit 47", useful until unit 47 is gone. And the janitor only empties the unit when every label is gone and nobody is standing inside it.

"I deleted a large log file but the disk is still full. Why?"

"Because deleting removes a name, not the data. The inode holds the data and a count of how many references point at it — directory entries and open file handles both count. If a process still has that log open, the link count has not reached zero, so the kernel keeps the blocks allocated even though the filename is gone. lsof will show the deleted file still held open. Restarting or signalling the process to reopen its log releases the space, which is also the reason log rotation tools send a signal after rotating rather than just moving the file."

Daemons

Systemd

The modern Linux init system.
Typical Node.js systemd service file (/etc/systemd/system/api.service)
[Unit]
Description=Backend API Service
After=network.target

[Service]
Type=simple
User=appuser
WorkingDirectory=/var/www/api
Environment=NODE_ENV=production
ExecStart=/usr/bin/node dist/server.js
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target

Q&A

Interview Questions

The classic OS probes.
"What happens when you run node app.js?"

"The shell uses fork() to create a child process, then exec() to replace that child with the node binary, passing app.js as an argument. The OS allocates a virtual memory space (stack, heap, code segments), opens standard file descriptors (stdin, stdout, stderr), and hands control to the Node.js V8 engine, which initializes the event loop and begins parsing app.js."
