Transport

TCP/IP Basics

The reliable pipe of the internet.

TCP vs UDP

TCP: Reliable, ordered, error-checked, connection-oriented. High overhead. (Used for HTTP, SSH).
UDP: Unreliable, unordered, connectionless. Fast. (Used for WebRTC media streams, DNS).

The 3-Way Handshake

Client sends SYN (synchronize).
Server replies with SYN-ACK.
Client replies with ACK (acknowledge). Connection established.

Congestion Control

TCP slows down if it detects dropped packets, ensuring the network isn't overwhelmed. (Slow Start phase).

03
Security

TLS/SSL

Encryption in transit.

TLS Handshake

1. Client Hello (cipher suites supported). 2. Server Hello + Certificate (public key). 3. Client verifies cert. 4. Key Exchange (symmetric session key created). 5. Encrypted communication begins.

mTLS (Mutual TLS)

Not just the client verifying the server, but the server also verifying the client's certificate. Common in zero-trust architectures and service-to-service communication.

Resolution

DNS Architecture

The phonebook of the internet.
1. Check local browser cache, then OS cache.
2. OS queries the ISP's Recursive Resolver.
3. Resolver queries the Root Nameserver (.), which points to the TLD (.com).
4. TLD Nameserver points to the Authoritative Nameserver (example.com).
5. Authoritative Server returns the A Record (IP address). Resolver caches it.

A vs AAAA

A maps to IPv4. AAAA maps to IPv6.

CNAME vs ALIAS

CNAME maps a domain to another domain. Cannot be used at the root (apex) level. ALIAS/ANAME solves this.

WebSockets & Real-time

Used in Forever Yours & Gaza40+.

The Upgrade

Starts as a standard HTTP/1.1 request with the Upgrade: websocket header. If the server accepts (101 Switching Protocols), the TCP connection stays open.

Scaling WebSockets (The hard part)

Since connections are stateful, load balancers must use Sticky Sessions or be configured for long-lived connections. When running multiple server instances, you must use a pub/sub backplane (like Redis) so an event on Server A reaches a client connected to Server B.

API Protocols

REST, GraphQL, gRPC, webhooks — and the question that actually picks between them.

These get compared as if one is modern and the others are legacy. The more useful framing is that each one optimizes a different axis, and the choice follows from who the client is and what the traffic looks like. Say that first and the comparison becomes a design discussion instead of a preference.

The HTTP semantics people get wrong

Safe means the call does not change state — GET, HEAD. Idempotent means making the call twice leaves the same state as making it once. These are different properties and the second one is the one that matters operationally.

PUT and DELETE are idempotent by definition: setting a resource to a value twice, or deleting it twice, ends in the same state. POST is not, which is exactly why double-clicking a submit button can create two orders. Every retry mechanism — a client retry, a load balancer retry, a queue redelivery — depends on idempotency, so if the operation is not naturally idempotent you have to make it so with an idempotency key: the client sends a unique id, the server records it with the result, and a repeat of the same key returns the stored result instead of doing the work again. This is how payment APIs stay safe under retries, and it is a strong thing to mention unprompted.

Status codes that carry real information

201 with a Location header for a created resource. 202 when you accepted the work but have not done it yet — the honest answer for anything queued. 409 for a conflict with current state, which is the right answer for a duplicate submission. 422 when the request parsed but the contents are invalid, as opposed to 400 for malformed. 429 with Retry-After, which turns a rate limit into something a client can obey. The difference between 401 (I do not know who you are) and 403 (I know, and no) gets asked often.

Versioning

The decision is less about URL versus header and more about what counts as a breaking change. Adding an optional field is safe if clients ignore unknown fields; removing a field, renaming one, tightening validation, or changing a default is not. URL versioning (/v1/) is explicit, trivially routable, and what most public APIs use. Header versioning keeps URLs stable and is tidier in theory, but it is easier to get wrong in caches and harder to debug from a browser. Pick URL versioning unless you have a specific reason, and treat additive change as the way to avoid needing a new version at all.

Pagination

Offset pagination (LIMIT 20 OFFSET 4000) is simple and degrades badly: the database still walks the skipped rows, so deep pages get slower, and if a row is inserted while a user pages through they will see an item twice or miss one. Cursor pagination passes an opaque marker for the last item seen and translates to WHERE id > ?, which stays fast at any depth and is stable under concurrent inserts. Offset is fine for an admin table of a few hundred rows; cursors are the right default for a feed or any large list.

"How would you make a payment webhook safe?"

"Three things, and they are all about not trusting the request. First, verify the signature — the provider signs the raw body with a shared secret, so I have to compute the HMAC over the exact bytes received before any JSON parsing, since re-serializing changes them. Second, idempotency: delivery is at-least-once, so duplicates are expected rather than exceptional. I store the provider's event id and make processing conditional on inserting it, so a replay is a no-op instead of a second order. Third, respond fast and do the work asynchronously — acknowledge with a 2xx, push the job onto a queue, and let a worker handle it, because providers time out and retry, and a slow handler turns into a storm of duplicate deliveries."

Real-World Debugging

Tools for diagnosing network failures.
"An API request is failing in production but works locally. How do you debug it?"

"First, I'd check the exact network request in the browser dev tools, looking at the HTTP status code and response body. If it's a CORS error, I check the preflight OPTIONS request. If it's a 502/504, I check the ALB/Nginx proxy logs to see if the backend is down or timing out. I would use curl -v to inspect headers and the TLS handshake, and dig to confirm DNS is resolving to the correct load balancer IP."
