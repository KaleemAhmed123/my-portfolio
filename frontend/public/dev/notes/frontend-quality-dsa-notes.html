UX

Forms, file uploads, and dashboards

Resume projects depend on reliable operational interfaces.

Validation

Use client validation for UX and server validation for security. Zod schemas can align frontend and backend rules.

File Uploads

Validate size/type, use pre-signed URLs for large files, show progress, scan risky documents, store metadata in DB.

Dashboards

Design for filtering, sorting, status visibility, empty states, permission boundaries, and fast scanning.

Error Boundaries

Contain UI crashes, report to Sentry, and show recovery actions instead of blank screens.

"How would you design the Gaza40+ admin dashboard?"

"I would optimize for case triage: filters by region/status/urgency, profile completeness, document verification, funding gap, assigned mentor, and latest activity. Permissions must scope regional admins to their region, while master admins see global dashboards. Every status transition should be auditable."

03
Quality

API testing and frontend resilience

Quality is observable behavior, not only unit tests.
Postman: test auth flows, CRUD, validation errors, pagination, RBAC denial, webhooks, and payment callbacks.
Jest: test pure functions, services, validators, hooks, and edge cases.
Contract tests: protect frontend/backend agreement for response shape and error codes.
Error boundaries: catch rendering failures and report useful context.
Logging: include request IDs and user/session context without leaking secrets.

Deep Reference

Frontend, testing, and DSA reference

Enough depth to discuss full-stack decisions, not just UI libraries.

How to position frontend experience

You are not trying to sound like a pure UI specialist. The strong narrative is: "I can build operational interfaces that expose backend workflows safely: dashboards, forms, uploads, role-based views, and API-integrated flows. I understand rendering tradeoffs and how frontend choices affect backend load and user correctness."

"How do you choose between SSR and CSR?"

SSR is useful when first content, SEO, or secure server-side data fetching matters. CSR is fine for authenticated dashboards where interactivity dominates and SEO is irrelevant. I also consider API load, caching, loading states, and whether the data is user-specific or public.

RC
React

React architecture patterns

Good React code separates data, state, and presentation.

Component boundaries

Split by responsibility: page/container fetches data and owns workflow; presentational components render; form components manage validation; hooks isolate reusable behavior.

Custom hooks

Good for repeated client-side logic such as pagination, debounced search, file upload progress, auth state, websocket subscription, and mutation handling.

Hook responsibilities
usePaginatedOrders()
- owns cursor/page state
- calls API
- exposes data, loading, error, fetchNext
- does not render UI directly

State placement

Keep state as local as possible. Use URL state for filters/search that should be shareable. Use server state libraries or explicit fetching for API data. Avoid global state for everything.

Performance

Memoization is not the first tool. First avoid unnecessary data fetching, large client bundles, huge lists without virtualization, and expensive renders in frequently updated components.

FOR
Forms

Forms, validation, uploads, and workflow UX

Most business apps are form and status workflows.
Client renders form with clear required fields, defaults, loading state, optimistic or pessimistic submission behavior, and field-level errors.
Client validates for usability, but server validates again for security and correctness.
Server returns machine-readable error codes and field-level messages. Frontend maps them predictably.
For file uploads, large files should go through pre-signed object storage upload when possible, with metadata saved through backend API.
Every admin workflow should have status visibility: draft, submitted, under_review, approved, rejected, needs_info.

TST
Testing

Testing pyramid for your resume projects

Know what to test and at which layer.

Unit tests

Best for pure logic: commission calculation, funding gap calculation, validators, mappers, status transition guards, date formatting, permission checks.

Integration tests

Use for real database constraints, transactions, file metadata, auth middleware, queue consumer behavior, and API endpoints with test DB.

Contract/API tests

Postman collections or automated contract tests should verify request/response shape, error codes, auth, pagination, and role restrictions.

E2E tests

Keep few and valuable: login, upload document, admin review, checkout/payment simulation, webhook handling, and dashboard visibility.

"What would you test in Gaza40+?"

I would test role-based access, regional scoping, document upload validation, profile completeness, offer verification transitions, funding gap calculations, mentor assignment, dashboard filters, and audit logs. The highest-risk bug is a regional admin seeing or modifying a student outside their region.

DP answer framework

  • Define state clearly: dp[i] or dp[i][j] means what exactly?
  • Define transition: how current state depends on previous states.
  • Define base cases.
  • Pick iteration order so dependencies are computed first.
  • Analyze time and space; optimize space only after correct solution.

How DSA connects to backend

Hashing relates to sharding and idempotency maps. Queues relate to BFS and workers. Heaps relate to scheduling/retries. Graphs relate to service dependencies. DP trains state modeling, useful for workflow state machines.

BEH
Behavioral

Project storytelling framework

Make answers concrete and measurable.
Context: what was the product/business problem and who were the users?
Constraints: scale, time, external APIs, correctness, security, team size, infrastructure.
Decision: architecture chosen and why alternatives were rejected.
Implementation: specific components, data models, failure handling, tests, observability.
Result: measurable impact, reliability, reduced manual work, faster workflow, fewer errors.
Learning: what you would improve now.
"Tell me about a challenging project."

Choose the ETL platform or Personalized Wallah. Start with the business problem, then explain why simple CRUD was not enough: cross-system consistency, duplicate prevention, partial failures, external API retries, and operational visibility. End with measurable impact and a specific improvement you would make next, such as outbox pattern, stronger contract tests, or better dashboards.
