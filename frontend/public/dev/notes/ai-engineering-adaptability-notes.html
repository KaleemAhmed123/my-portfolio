AI Engineering Interview Notes

This page turns the resume's AI engineering and adaptability section into defendable interview knowledge: what you built, how you control risk, how you evaluate outputs, and how you use AI without giving up engineering ownership.

01
Positioning

Your AI narrative

AI-assisted, not AI-led.

The best framing is: I use AI to accelerate engineering, but I remain accountable for architecture, correctness, security, product taste, and final decisions. This avoids sounding like a tool user and positions you as an engineer who can work well in an AI-first environment.

Engineering Ownership

AI can draft, summarize, generate tests, or explore options. You still review, run, measure, and decide.

Product Taste

Judge whether output fits user workflow, domain constraints, edge cases, and maintainability.

Safety

Never paste secrets. Review generated code for auth, injection, performance, dependencies, and licensing issues.

Adaptability

Learning speed matters, but so does discipline: small experiments, evidence, feedback loops, and sustainable health.

LLMs are probabilistic components; wrap them with deterministic systems.

"How do you reduce hallucinations in an LLM extraction system?"

Strong answer: "I constrain the task to extraction, provide schema-based output, ask for source evidence, validate the JSON, reject unsupported fields, and route low-confidence fields to human review. The system should prefer blank/unknown over invented values."

03
RAG

Retrieval-augmented generation

RAG is search plus generation plus evaluation.

Indexing

  • Chunk documents by semantic boundaries
  • Store embeddings plus metadata
  • Keep source document IDs and versions

Retrieval

  • Use top-k vector search, filters, hybrid search
  • Re-rank when precision matters
  • Return citations/source spans

Generation

  • Answer only from retrieved context
  • Say "not enough information" when context is weak
  • Keep context under token budget

Evaluation

  • Retrieval precision/recall
  • Faithfulness to sources
  • Golden question set and regression tests
Interview distinction

Fine-tuning changes model behavior. RAG injects external knowledge at query time. For business documents that change often, RAG is usually the first choice because it is cheaper to update the index than retrain a model.

05
Evaluation

How to prove AI output is good

AI systems need tests, not vibes.
Golden set: representative inputs with expected outputs, including edge cases and adversarial examples.
Schema validity: percentage of outputs that parse and pass business validation.
Field accuracy: precision/recall for extracted fields, especially high-risk fields like names, dates, policy numbers, amounts.
Faithfulness: answer must be supported by source spans. Unsupported claims are failures.
Cost and latency: tokens, model latency, retry rate, timeout rate, and queue backlog.
Human override rate: how often users correct AI output; use corrections to improve prompts/retrieval.
06
Adaptability

Behavioral answer bank

Prepare crisp answers that sound mature, not buzzword-heavy.
"How do you use AI in your engineering workflow?"

"I use AI as a force multiplier for exploration, boilerplate, test ideas, documentation, and alternative designs. I do not treat output as truth. I review assumptions, run tests, inspect security and performance risks, and keep final ownership. The fastest workflow is still disciplined: clarify the problem, generate options, verify with evidence, and ship only what I understand."

"What does adaptability mean to you in an AI-first engineering world?"

"Adaptability is not chasing every tool. It is learning quickly while preserving judgment. I try small experiments, compare outputs against real requirements, keep health and focus stable, and build taste by reviewing what AI produces instead of blindly accepting it."

Avoid saying

Do not say "AI writes most of my code." Say AI accelerates parts of the workflow, but architecture, correctness, security, and final decisions remain yours.

07
Deep Reference

AI engineering project-building reference

For Acordly, RAG, agent workflows, MCP tools, and AI-assisted development interviews.

The correct mental model

An AI feature is not just an API call to a model. It is a system made of input preparation, retrieval or context selection, prompting, model execution, structured output parsing, validation, human review, monitoring, cost control, and feedback loops. The model is one component inside a larger deterministic product workflow.

OCR
Acordly

OCR + LLM extraction pipeline

A practical architecture for insurance document automation.
User uploads document. Backend validates file type, size, tenant, and permissions, then stores original file in object storage with metadata.
OCR service runs AWS Textract or Google Vision. Store extracted text blocks, coordinates, page number, confidence, and source document version.
Preprocessor cleans OCR noise, groups sections, normalizes whitespace, and detects candidate document type or ACORD form type.
LLM receives a constrained extraction prompt, allowed field schema, examples, and OCR context. It returns structured JSON only.
Validator checks JSON schema, field types, enum values, required fields, confidence, and source evidence. Unsupported fields become blank or review-needed.
Form mapper converts extracted facts into ACORD field IDs. User reviews low-confidence or high-risk fields before final form generation.
Audit log records input file, model version, prompt version, output, corrections, and final submitter for compliance and debugging.

OCR misses textUse OCR confidence, page preview, manual correction, fallback OCR provider for important documentsOCR confidence by page, manual correction rate

PR
Prompting

Prompt engineering that survives production

Good prompts define contracts, not vibes.

Prompt components

  • Role: what perspective the model should take, such as "insurance document extraction assistant".
  • Task: exact operation, such as "extract only fields supported by the supplied document text".
  • Schema: required JSON keys, allowed enum values, confidence format, evidence/source span format.
  • Rules: do not infer missing data, do not use outside knowledge, prefer null/unknown over guessing.
  • Examples: one or two representative inputs with expected outputs for tricky fields.
  • Failure behavior: what to do when the document is unreadable, ambiguous, or unrelated.

Prompt versioning

Treat prompts like code. Store prompt version, model name, temperature, schema version, and evaluation results. A changed prompt can break extraction just like a changed API.

Temperature

Use low temperature for extraction, classification, and deterministic workflows. Higher temperature is useful for ideation, not for filling insurance forms or financial records.

Extraction prompt contract
System:
You extract insurance form data from OCR text.
Return JSON matching the schema. Do not invent values.
If evidence is missing, set value to null and confidence to 0.

User:
Form type candidates: ACORD_25, ACORD_125
Allowed fields:
- insured_name: string
- policy_number: string | null
- effective_date: ISO date | null

For each field return:
{ "value": ..., "confidence": 0-1, "evidence": "short source quote", "page": number }
RAG
Retrieval

RAG design in detail

Retrieval quality dominates answer quality.
Ingestion loads source documents, strips boilerplate, preserves document ID, tenant ID, version, permissions, and timestamps.
Chunking splits documents by heading/section/semantic boundary. Avoid chunks so small they lose meaning or so large they waste context.
Embedding converts chunks to vectors. Store vectors with metadata filters for tenant, document type, date, owner, and permission scope.
Query processing rewrites or expands the user query when needed, applies filters, retrieves top-k candidates, and optionally reranks.
Generation receives only selected context and must cite sources. If context is insufficient, the answer should say so.
Evaluation checks retrieval hit rate, answer faithfulness, citation correctness, latency, and cost.
"Why is my RAG system hallucinating even though I added documents?"

Because adding documents is not enough. Retrieval may be missing the right chunks, chunks may lack context, metadata filters may be wrong, or the prompt may allow unsupported claims. I would inspect retrieved chunks for failed questions, add a golden evaluation set, improve chunking/reranking, require citations, and make the model answer "not enough information" when evidence is weak.

EV
Evaluation

AI evaluation framework

Know how to measure model behavior before and after changes.

Offline eval

Run a fixed golden dataset before release. Track parse success, exact field match, semantic correctness, faithfulness, refusal correctness, and latency/cost.

Online eval

Track user corrections, thumbs up/down, escalation rate, retry rate, low-confidence rate, abandonment, and time saved per workflow.

Regression testing

Every prompt/model/retrieval change should be tested against previous failures. AI changes can regress silently if you only test happy paths.

Human-in-loop threshold

Not all fields need the same confidence. High-risk fields such as policy number, dates, money, legal names, and coverage limits need stricter thresholds.

DEV
AI-Assisted Development

How to talk about tools like Claude, Codex, N8N, Antigravity

The mature answer emphasizes leverage plus judgment.
Use AI for: design alternatives, scaffolding, test cases, refactoring suggestions, documentation drafts, API client examples, debugging hypotheses.
Do not outsource: security decisions, architecture ownership, production deploys, data migrations, auth logic, payment correctness, customer communication.
Verification loop: read generated code, run tests, inspect diffs, check edge cases, compare to requirements, measure performance where relevant.
Prompting workflow: provide context, constraints, acceptance criteria, examples, and ask for risks/tradeoffs before code.
Tool choice: use N8N for low-risk workflow automation; use custom backend code for core business correctness and complex domain rules.
"What is the biggest risk with AI-assisted development?"

The biggest risk is false confidence. AI can produce plausible code that is subtly wrong, insecure, inefficient, or inconsistent with the existing system. My mitigation is to keep human ownership: understand the change, run tests, review security and edge cases, and use AI as a reviewer or accelerator rather than an authority.
