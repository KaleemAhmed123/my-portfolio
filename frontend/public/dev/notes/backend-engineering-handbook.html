Concurrency

Race conditions, locks, and the art of not shooting yourself in the foot

Core Concept

Concurrency means multiple operations happening at the same time, or appearing to. In development you test with one user. In production, a thousand requests hit your server simultaneously. Things that work perfectly in isolation break spectacularly together.

The classic problem: two users try to buy the last item in your inventory at the exact same millisecond. Both read stock = 1, both decide they can proceed, both decrement — now stock is -1. You've oversold. Welcome to a race condition.

🎭 Analogy

Two people editing the same Google Doc offline, then both saving. Whoever saves last wins — the other person's changes vanish. Concurrency bugs are that "last save wins" problem, except in your database with money or inventory on the line.

Key Concepts

🔒

Mutex / Lock

Only one thread can hold the lock at a time. Others wait. Use for short critical sections.

⚛️

Atomic Operations

CPU-level operations that can't be interrupted. INCR in Redis is atomic — guaranteed.

😊

Optimistic Locking

Assume no conflict. Check version on write. Retry on conflict. Good for low-contention.

😠

Pessimistic Locking

Assume conflict. Lock immediately. Others block. Good for high-contention writes.

🔄

Event Loop

Node.js runs one JS thread. I/O is async. Concurrency via callbacks, not threads.

🏦

Isolation Levels

READ COMMITTED, REPEATABLE READ, SERIALIZABLE — trade consistency for performance.

Code Example

SQL + Node.jsPreventing oversell with pessimistic locking
-- Pessimistic: lock the row immediately, block concurrent reads
BEGIN;
SELECT stock FROM products WHERE id = 42 FOR UPDATE;  -- row is now locked
-- application checks: if stock > 0, proceed
UPDATE products SET stock = stock - 1 WHERE id = 42;
INSERT INTO orders (product_id, user_id) VALUES (42, 99);
COMMIT;
-- Lock is released. Next waiter proceeds.
SQLOptimistic locking with version column
-- Optimistic: no lock on read. Check version on write.
SELECT stock, version FROM products WHERE id = 42;
-- Got: stock=1, version=5

UPDATE products
  SET stock = stock - 1, version = version + 1
  WHERE id = 42 AND version = 5;  -- version guard

-- If 0 rows updated → someone else changed it → RETRY
-- If 1 row updated → success!
RedisAtomic decrement — race-condition-free inventory
-- Redis DECRBY is atomic. No two clients can interleave.
DECRBY inventory:42 1
-- Returns new value. If < 0, rollback: INCRBY inventory:42 1

-- Or use Lua script for check-and-decrement atomically:
local stock = redis.call('GET', KEYS[1])
if tonumber(stock) > 0 then
  return redis.call('DECRBY', KEYS[1], 1)
end
return -1  -- out of stock signal
⚡ Production Tips
  • Prefer atomic DB operations (UPDATE with WHERE) over read-then-write patterns whenever possible.
  • Use Redis INCR/DECR for counters — it's single-threaded and race-free by design.
  • Keep pessimistic locks as short as possible — long locks = long queues = timeouts.
  • Set lock timeouts. A crashed process should not hold a lock forever.
  • In Node.js, the event loop handles concurrency without threads — but CPU-bound tasks block it. Use worker_threads for heavy computation.
  • Test concurrency with tools like k6 or Apache JMeter — run 100 simultaneous requests and verify correctness.
🎯 Interview Prep
"Two users try to buy the last item simultaneously. How do you prevent overselling?"
✗ Weak

"I'd use a transaction."

✓ Strong

"I'd use a SELECT FOR UPDATE (pessimistic lock) inside a transaction. Both users hit the endpoint simultaneously — the first one acquires the row lock and checks stock, the second blocks. When the first commits, the second proceeds but now sees stock = 0 and gets an 'out of stock' error. For high-traffic flash sales, I'd move inventory to Redis and use Lua scripting for an atomic check-and-decrement — much faster than a DB row lock and no connection pool exhaustion."

"What's the difference between optimistic and pessimistic locking?"
✓ Strong

"Pessimistic locking says 'I expect conflict — lock immediately.' It's safe but creates contention. Optimistic says 'conflict is rare — proceed without a lock, but verify on write via a version column.' If the version changed, retry. I use optimistic for low-contention scenarios like user profile edits, and pessimistic for high-contention scenarios like inventory or wallet balances."

Transactions

All or nothing — the backbone of payment systems

Core Concept

A transaction is a group of operations that succeed together or fail together. When you deduct money from one account and add it to another, both must happen — you can't have money disappear or materialize from thin air.

Databases guarantee this through ACID properties. Miss any one of them and you're building on sand.

🎭 Analogy

A transaction is like a bank wire transfer. The bank doesn't take money from your account and say "okay we'll add it to the recipient's account later." Both sides happen atomically, or neither does. If the system crashes mid-transfer, the whole thing rolls back.

ACID Properties

A — Atomicity

All operations succeed, or none of them do. No partial states.

C — Consistency

The DB goes from one valid state to another. Constraints never violated.

I — Isolation

Concurrent transactions don't see each other's uncommitted changes.

D — Durability

Committed data survives crashes. Written to disk, not just memory.

Code Examples

Node.js + PostgreSQLPayment transfer — atomic debit + credit
async function transfer(fromId, toId, amount) {
  const client = await pool.connect();
  try {
    await client.query('BEGIN');

    const { rows } = await client.query(
      `SELECT balance FROM accounts WHERE id = $1 FOR UPDATE`,
      [fromId]
    );

    if (rows[0].balance < amount) {
      throw new Error('Insufficient funds');
    }

    await client.query(
      `UPDATE accounts SET balance = balance - $1 WHERE id = $2`,
      [amount, fromId]
    );
    await client.query(
      `UPDATE accounts SET balance = balance + $1 WHERE id = $2`,
      [amount, toId]
    );
    await client.query(
      `INSERT INTO transactions (from_id, to_id, amount) VALUES ($1, $2, $3)`,
      [fromId, toId, amount]
    );

    await client.query('COMMIT');
    return { success: true };
  } catch (err) {
    await client.query('ROLLBACK'); // entire transaction undone
    throw err;
  } finally {
    client.release();
  }
}

Isolation Levels

LevelDirty ReadNon-Repeatable ReadPhantom ReadUse When
READ UNCOMMITTEDPossiblePossiblePossibleAnalytics where stale is OK
READ COMMITTEDSafePossiblePossibleDefault in Postgres, most apps
REPEATABLE READSafeSafePossibleReports needing stable snapshot

⚡ Production Tips
  • Keep transactions short — a long open transaction holds locks, blocks other queries, and can cause connection pool exhaustion.
  • Never do network calls (HTTP, email) inside a DB transaction. The external call may hang for 10s while your lock is held.
  • Use Savepoints for nested transaction-like behavior within a single transaction.
  • Deadlock detection: Postgres auto-detects and kills the younger transaction. Retry on deadlock errors (SQLSTATE 40P01).
  • Distributed transactions (across multiple DBs/services) are notoriously hard. Prefer the Saga pattern — a sequence of local transactions with compensating actions.
🎯 Interview Prep
"What does ACID stand for and why does it matter?"
✓ Strong

"ACID ensures database correctness. Atomicity means all-or-nothing — a payment can't debit without crediting. Consistency means constraints are always satisfied. Isolation means concurrent transactions don't step on each other's toes — critical for correctness under load. Durability means a committed transaction survives a crash — we don't lose data when a server reboots. In practice, I've seen teams skip proper transaction scoping and end up with ghost orders where money was deducted but the order wasn't created. ACID is what prevents that."

"What are the risks of long-running transactions?"
✓ Strong

"Long transactions hold locks on rows and pages, blocking other writers. They can also bloat the transaction log and in Postgres, prevent VACUUM from cleaning dead rows — table bloat. In high-traffic apps I always aim for sub-50ms transactions. If something expensive must happen, I'll complete the DB work first, commit, then do the external operation."

Database Indexing

The difference between O(log n) and a full table scan at 10M rows

Core Concept

An index is a separate data structure that stores a sorted copy of one or more columns, with pointers back to the original rows. When you query by an indexed column, the DB uses the index instead of scanning every row.

Without an index on a 10-million-row table, WHERE email = 'user@example.com' reads all 10 million rows. With a B-tree index, it's ~25 comparisons. That's the difference between a 5-second query and a 1ms query.

🎭 Analogy

A database index is exactly like the index at the back of a textbook. Without it, to find all mentions of "TCP/IP" you'd read every single page. With the index, you jump directly to page 247, 312, and 401. The B-tree structure is how that index is organized — sorted alphabetically for fast binary search.

Code Examples

SQLIndex types and when to use them
-- Single column index: fast WHERE email = ?
CREATE INDEX idx_users_email ON users(email);

-- Composite index: fast for (user_id + status) or just user_id
-- Leftmost prefix rule: this helps WHERE user_id = ? AND status = ?
-- Also helps WHERE user_id = ? (alone)
-- Does NOT help WHERE status = ? (alone)
CREATE INDEX idx_orders_user_status ON orders(user_id, status);

-- Covering index: all needed cols in the index → no table lookup
-- Query: SELECT email, name FROM users WHERE email = ?
-- If index covers email + name → result served from index alone
CREATE INDEX idx_covering ON users(email) INCLUDE (name);

-- Partial index: only index rows matching condition
-- Great for "pending orders" queries on a table with mostly completed
CREATE INDEX idx_pending ON orders(created_at)
  WHERE status = 'pending';

-- EXPLAIN ANALYZE: see if your index is being used
EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'test@example.com';
-- Look for: "Index Scan" (good) vs "Seq Scan" (bad on large tables)

B-tree Index Structure

A B-tree (Balanced Tree) is the default index type. Data is stored in sorted order across multiple pages. Each node has multiple keys and pointers. The tree stays balanced — all leaves are at the same depth. This guarantees O(log n) lookups regardless of data size.

Key insight: B-trees support equality (=), range (> < BETWEEN), and prefix (LIKE 'abc%') queries. They do NOT support suffix patterns (LIKE '%abc') — that requires a full scan or a special index like GIN.

⚡ Production Tips
  • Indexes slow down writes (INSERT/UPDATE/DELETE must update the index too). Don't over-index — be selective.
  • High cardinality columns (email, user_id) benefit most from indexes. Low cardinality (boolean, status with 3 values) often doesn't help.
  • Run EXPLAIN ANALYZE on slow queries — look for "Seq Scan" on large tables as the smoking gun.
  • In Postgres, use pg_stat_user_indexes to find unused indexes — they're write overhead with no read benefit.
  • Create indexes CONCURRENTLY in production to avoid table locks during creation.
  • The composite index column order matters: put the most selective column first, equality conditions before range conditions.
🎯 Interview Prep
"A query that was fast is now slow after reaching 10 million rows. What do you check?"
✓ Strong

"First, I'd run EXPLAIN ANALYZE to see the query plan. I'm looking for a Seq Scan on a large table — that's usually the culprit. Then I'd check if there's an index on the WHERE columns. If there is but it's not being used, the query planner might have decided a seq scan is faster — common when you're fetching a large percentage of rows, or the index statistics are stale (run ANALYZE). I'd also check for function calls on indexed columns like WHERE LOWER(email) = ? — that disables index usage. The fix would be a functional index or changing the query."

Caching

The fastest database query is the one you never make

Core Concept

Caching stores frequently-accessed data in fast memory (Redis, Memcached) so you don't hit the database on every request. A Redis GET takes ~0.1ms. A Postgres query might take 5–50ms. At 10,000 req/sec, that difference is what separates a working system from a melted one.

The challenge isn't storing data in cache — it's cache invalidation: knowing when cached data is stale and needs to be refreshed. Phil Karlton famously said: "There are only two hard things in computer science: cache invalidation and naming things."

🎭 Analogy

A cache is like your brain's short-term memory vs. looking something up in a book. You remember your friend's phone number (cache hit — instant). For a rarely-called number, you look it up in your contacts (cache miss — go to the source). If your friend changes their number but you still have the old one memorized, that's a stale cache.

Caching Patterns

Cache-Aside (Lazy)

App checks cache first. Miss → fetch DB → populate cache. Most common pattern.

Write-Through

Write to cache AND DB simultaneously. Cache always fresh. Slower writes.

Write-Behind

Write to cache immediately, DB async. Fast writes but risk of data loss.

Read-Through

Cache sits in front of DB. Cache handles misses automatically.

Code Examples

Node.js + RedisCache-aside pattern with TTL
async function getUserById(userId) {
  const cacheKey = `user:${userId}`;

  // 1. Check cache first
  const cached = await redis.get(cacheKey);
  if (cached) {
    return JSON.parse(cached);  // cache hit ✓
  }

  // 2. Cache miss → fetch from DB
  const user = await db.query(`SELECT * FROM users WHERE id = $1`, [userId]);

  // 3. Populate cache with TTL (5 minutes)
  await redis.setex(cacheKey, 300, JSON.stringify(user));

  return user;
}

// Invalidation on update — critical!
async function updateUser(userId, data) {
  await db.query(`UPDATE users SET ... WHERE id = $1`, [userId]);
  await redis.del(`user:${userId}`); // evict stale cache
}
RedisCache stampede protection (mutex)
// Cache stampede: cache expires, 1000 concurrent requests all hit DB
// Fix: only one request rebuilds the cache, others wait

async function getWithStampedeProtection(key, fetchFn, ttl = 300) {
  const cached = await redis.get(key);
  if (cached) return JSON.parse(cached);

  // Try to acquire rebuild lock
  const lockKey = `lock:${key}`;
  const acquired = await redis.set(lockKey, 1, 'NX', 'EX', 10);

  if (acquired) {
    const data = await fetchFn();           // only ONE request hits DB
    await redis.setex(key, ttl, JSON.stringify(data));
    await redis.del(lockKey);
    return data;
  } else {
    // Another request is rebuilding. Wait and retry.
    await sleep(100);
    return getWithStampedeProtection(key, fetchFn, ttl);
  }
}
⚡ Production Tips
  • Set meaningful TTLs. Too short = high cache miss rate. Too long = stale data. Profile your data's change frequency.
  • Use cache tags or key prefixes for bulk invalidation: user:* to clear all user caches.
  • Cache stampede is real in high-traffic systems. Use mutex locks or probabilistic early expiration (PER algorithm).
  • Monitor cache hit rate. A good cache hit rate is >90%. Below 80% means your TTL is too short or your access patterns are too random.
  • Redis eviction policy: set maxmemory-policy allkeys-lru so Redis evicts least-recently-used keys when full, rather than crashing.
  • Don't cache user-specific data at the application level if using a shared cache — namespace by user ID.
🎯 Interview Prep
"Your database is overloaded during peak traffic. How do you reduce the load?"
✗ Weak

"I'd add Redis."

✓ Strong

"I'd implement cache-aside pattern with Redis. For each hot query (like product listings or user profiles), check cache first. On a miss, query the DB and cache the result with an appropriate TTL — maybe 5 minutes for products, 1 hour for configs. I'd also set up cache warming to pre-populate on deployment so the cold start after deploy doesn't spike the DB. I'd add stampede protection for critical high-traffic endpoints. The goal is a 90%+ cache hit rate, which should reduce DB load by 10x."

Rate Limiting

Protecting your API from bots, abuse, and well-meaning but destructive clients

Core Concept

Rate limiting restricts how many requests a client can make in a time window. Without it, a single bot can hammer your API with 10,000 requests/second and take down your service for everyone else.

Rate limiting protects against: DDoS attacks, credential stuffing, scraping bots, runaway clients with bugs making infinite retry loops, and free-tier abuse.

🎭 Analogy

A token bucket is like a bus ticket machine. You start with 10 tokens in your bucket. Each request spends one token. Tokens refill at 2 per second. If you burst and empty the bucket, you wait for it to refill. This is how Stripe, GitHub, and most production APIs work.

Algorithms Compared

AlgorithmHow It WorksBurst AllowedBest For
Token BucketTokens added at rate r. Each request consumes 1. Excess rejected.Yes (up to bucket size)APIs allowing some burst
Leaky BucketRequests queue up, processed at fixed rate. Overflow dropped.No (smoothed output)Smooth traffic shaping
Fixed WindowCount requests per time window. Reset at boundary.Double at boundary!Simple use cases
Sliding WindowRolling window of last N seconds. More accurate than fixed.No double burstProduction standard

Code Example

Node.js + RedisSliding window rate limiter
async function isRateLimited(userId, limit = 100, windowSec = 60) {
  const key = `rl:${userId}`;
  const now = Date.now();
  const windowStart = now - (windowSec * 1000);

  const pipeline = redis.pipeline();
  pipeline.zremrangebyscore(key, 0, windowStart);  // prune old
  pipeline.zadd(key, now, `${now}-${Math.random()}`);  // add request
  pipeline.zcard(key);                               // count in window
  pipeline.expire(key, windowSec);                   // auto-clean keys
  const results = await pipeline.exec();

  const requestCount = results[2][1];
  return requestCount > limit;  // true = rate limited
}

// Express middleware usage
app.use(async (req, res, next) => {
  const limited = await isRateLimited(req.user.id);
  if (limited) {
    return res.status(429).json({
      error: 'Too Many Requests',
      retryAfter: 60  // always tell the client when to retry
    });
  }
  next();
});
⚡ Production Tips
  • Always return Retry-After and X-RateLimit-Remaining headers — clients can back off gracefully instead of hammering.
  • Rate limit by multiple dimensions: IP, user ID, API key. IP-only is bypassable via botnets.
  • Different limits for different endpoints: stricter on password reset/login (brute force prevention), looser on read endpoints.
  • Use API Gateway (AWS API Gateway, Kong, NGINX) for rate limiting at the infrastructure level — more reliable than application code.
  • Sliding window is worth the extra Redis cost vs. fixed window — fixed window has a 2x burst vulnerability at window boundaries.
🎯 Interview Prep
"How would you implement rate limiting for a public API?"
✓ Strong

"I'd use a sliding window counter in Redis, keyed by user ID or API key. For each request, I remove entries older than the window, add the current timestamp, and check the count. Redis sorted sets make this efficient. I'd expose rate limit headers so clients know their remaining quota. For unauthenticated endpoints, I'd rate limit by IP with a stricter limit. At scale, I'd push this to the API Gateway layer — application-level rate limiting doesn't protect against requests that consume resources before they hit your code."

Message Queues

Decoupling services so a slow email server doesn't crash your checkout

Core Concept

A message queue is a buffer between producers and consumers. Instead of Service A calling Service B directly and waiting, A publishes a message to the queue and moves on. B picks it up when it's ready.

This decoupling is the key insight. It means B can be slow, down, or overwhelmed — A still works fine. Messages pile up in the queue and get processed when B recovers.

🎭 Analogy

A restaurant's order slip system. The waiter takes your order (producer) and drops a slip in the kitchen window (queue). The chef (consumer) processes orders at their own pace. The waiter doesn't stand there waiting — they take more orders. If the kitchen is backed up, slips queue up. Nobody loses their order.

Code Example

Node.js + BullMQ (Redis-backed)Email job queue with retries
import { Queue, Worker } from 'bullmq';

// --- PRODUCER: enqueue in your API handler ---
const emailQueue = new Queue('emails', { connection: redisConfig });

async function signup(user) {
  await db.createUser(user);
  // Don't send email inline — enqueue it
  await emailQueue.add('welcome', { userId: user.id, email: user.email }, {
    attempts: 3,           // retry up to 3 times
    backoff: { type: 'exponential', delay: 2000 }
  });
  return res.json({ success: true }); // instant response
}

// --- CONSUMER: runs in a separate process ---
const worker = new Worker('emails', async (job) => {
  const { userId, email } = job.data;
  await sendWelcomeEmail(email);  // SMTP call here, not in API
  console.log(`Email sent to ${email}`);
}, { connection: redisConfig });

worker.on('failed', (job, err) => {
  console.error(`Job ${job.id} failed: ${err.message}`);
  // After 3 attempts, goes to Dead Letter Queue
});

Key Concepts

At-Least-Once Delivery

Message delivered at least once but possibly multiple times. Make consumers idempotent.

Dead Letter Queue

Failed messages after max retries land here for manual inspection. Never lose them.

Backpressure

Consumer signals it's overwhelmed. Producer slows down. Prevents memory blowup.

Ordering

Kafka guarantees order per partition. RabbitMQ with single consumer guarantees order. Multiple consumers = no ordering guarantee.

⚡ Production Tips
  • Make message handlers idempotent — at-least-once delivery means you will process duplicates. Processing the same message twice must be safe.
  • Always have a dead letter queue. Failed jobs need investigation, not silent disappearance.
  • Monitor queue depth. A growing queue is an early warning of a consumer falling behind.
  • BullMQ (Redis) for most apps. Kafka for high-throughput event streaming (millions/sec). RabbitMQ for complex routing (topics, fanout).
  • Include correlation IDs in messages for distributed tracing — trace a user action through all the async jobs it spawned.
🎯 Interview Prep
"Why not just send the welcome email synchronously in the signup handler?"
✓ Strong

"Three reasons. First, reliability: SMTP can fail or time out. If it does, the user gets an error even though their account was created — terrible UX. Enqueuing separates the concerns. Second, performance: email sending might take 2–5 seconds. The user shouldn't wait for that. Third, resilience: if the email service is down, messages queue up and get delivered when it recovers. The user gets their email 5 minutes late instead of never. The tradeoff is eventual delivery, which is almost always fine for emails."

Quick Reference

Background Workers

Don't make the user wait for things that can happen later

Core Concept

A background worker is a process that runs outside the request-response cycle. The API handler enqueues a job and returns immediately. The worker picks it up and does the heavy lifting asynchronously. This keeps your API fast and your users happy.

Use background workers for: PDF generation, video transcoding, sending emails/SMS, AI inference, image resizing, report generation, data exports, and anything that takes >500ms.

🎭 Analogy

When you order a custom cake at a bakery, they don't make you stand there while they bake it. They take your order (API responds), give you a ticket (job ID), and call you when it's ready (webhook/notification). The baker works in the background.

Node.jsPDF generation as background job
// API Handler — returns instantly with job ID
app.post('/reports/generate', async (req, res) => {
  const job = await reportQueue.add('generate-pdf', {
    userId: req.user.id,
    filters: req.body.filters
  });
  res.json({ jobId: job.id, status: 'queued' });
  // Response: 202 Accepted — processing in background
});

// Status polling endpoint
app.get('/reports/:jobId/status', async (req, res) => {
  const job = await reportQueue.getJob(req.params.jobId);
  const state = await job.getState(); // waiting/active/completed/failed
  res.json({ status: state, result: job.returnvalue });
});

// Background worker process
const worker = new Worker('reports', async (job) => {
  const pdfBuffer = await generatePDF(job.data);  // heavy operation
  const url = await s3.upload(pdfBuffer);
  await notifyUser(job.data.userId, url);         // webhook or email
  return { downloadUrl: url };
});
⚡ Production Tips
  • Use 202 Accepted (not 200) for endpoints that queue work — communicates async processing to clients.
  • Provide job status polling and/or webhooks so clients know when work completes.
  • Scale workers horizontally independently from your API servers — heavy batch processing doesn't slow down your API.
  • Set job timeouts — a stuck worker should be killed and retried, not held forever.
🎯 Interview Prep
"How would you handle generating a large PDF report for a user?"
✓ Strong

"I'd use a background job pattern. The API endpoint immediately returns a 202 with a job ID. A worker picks up the job, generates the PDF, uploads to S3, and sends the user a download link via email or webhook. I'd expose a status endpoint the client can poll. This keeps API response times fast regardless of report complexity."

Webhooks

Don't poll. Let the source tell you when something happens.

Core Concept

A webhook is an HTTP callback — you register a URL and an external service POSTs to it when an event occurs. Instead of you polling Stripe every second asking "did the payment succeed?", Stripe calls your endpoint the instant it does.

🎭 Analogy

Polling is like repeatedly calling a restaurant: "Is my food ready? Is it ready now? Now?" Webhooks are like leaving your phone number and having them call you when it's ready.

Node.jsStripe webhook with signature verification
// 1. Verify the signature — CRITICAL. Anyone can POST to your URL.
app.post('/webhooks/stripe',
  express.raw({ type: 'application/json' }),  // raw body needed for sig check
  async (req, res) => {
    const sig = req.headers['stripe-signature'];
    let event;
    try {
      event = stripe.constructEvent(req.body, sig, process.env.STRIPE_WEBHOOK_SECRET);
    } catch (err) {
      return res.status(400).send('Invalid signature');
    }

    // 2. Respond 200 immediately — tell Stripe you got it
    res.json({ received: true });

    // 3. Process async — don't do heavy work before responding
    switch (event.type) {
      case 'payment_intent.succeeded':
        await orderQueue.add('fulfill', event.data.object);
        break;
      case 'customer.subscription.deleted':
        await handleCancellation(event.data.object);
        break;
    }
  }
);
⚡ Production Tips
  • Always verify signatures. Without it, anyone can fake a "payment succeeded" event and get free access.
  • Respond with 200 immediately before doing any processing. If you respond slowly, the sender retries — causing duplicates.
  • Make handlers idempotent with a unique event ID check — store processed event IDs to prevent replay attacks.
  • Enqueue webhook processing as a background job — never do DB-heavy or slow work inline in the webhook handler.
  • Use a tool like ngrok in local development to expose your localhost to receive webhook events.
🎯 Interview Prep
"What's the difference between polling and webhooks? When would you use each?"
✓ Strong

"Polling is your client repeatedly asking a server 'anything new?' — simple but wasteful and latency-bound. Webhooks are event-driven: the server calls you. I'd use webhooks for payment events, third-party integrations, and anything where low latency matters and you control a public endpoint. I'd use polling when I can't register a callback URL (e.g., calling a third-party API that doesn't support webhooks), or for batch jobs where slight delays are fine. The key security practice for webhooks is signature verification to prevent spoofed events."

Authentication vs Authorization

Who are you? vs What can you do?

Core Concept

Authentication (AuthN): Verifying identity — "Who are you?" You prove who you are via password, token, biometric, etc.

Authorization (AuthZ): Verifying permission — "What are you allowed to do?" Once we know who you are, can you access this resource?

The confusion: both happen on every request, sequentially. First verify identity, then check permissions. Skipping either is a security hole.

🎭 Analogy

A hotel key card. Authentication is at the front desk — you show ID and they verify you're a guest (who you are). Authorization is when you tap your keycard on the room door — the door checks if your card is allowed into room 412 (what you can access). The front desk is AuthN. The door reader is AuthZ.

Node.js + JWTAuthN middleware → AuthZ check
// 1. AUTHENTICATION middleware — verify the JWT
const authenticate = (req, res, next) => {
  const token = req.headers.authorization?.split(' ')[1]; // "Bearer <token>"
  if (!token) return res.status(401).json({ error: 'Unauthorized' });
  try {
    req.user = jwt.verify(token, process.env.JWT_SECRET);
    next(); // identity confirmed: req.user.id, req.user.role
  } catch {
    res.status(401).json({ error: 'Invalid token' });
  }
};

// 2. AUTHORIZATION middleware — check role/permission
const authorize = (...roles) => (req, res, next) => {
  if (!roles.includes(req.user.role)) {
    return res.status(403).json({ error: 'Forbidden' });
  }
  next();
};

// 3. Resource-level check (does this user own this order?)
app.get('/orders/:id', authenticate, async (req, res) => {
  const order = await db.getOrder(req.params.id);
  if (order.userId !== req.user.id && req.user.role !== 'admin') {
    return res.status(403).json({ error: 'Forbidden' });
  }
  res.json(order);
});

// Admin-only route
app.delete('/users/:id', authenticate, authorize('admin'), async (req, res) => {
  await db.deleteUser(req.params.id);
  res.json({ success: true });
});

JWT Deep Dive

A JWT (JSON Web Token) is a self-contained token — it carries the user's identity and claims (id, role, email) encoded and signed with a secret. The server doesn't need to look up the session in a DB — it just verifies the signature.

Header

Algorithm type: {"alg":"HS256","typ":"JWT"}

Payload

Claims: {"sub":"123","role":"admin","exp":1234}

Signature

HMAC-SHA256 of header + payload + secret. Tamper-proof.

Refresh tokens: JWTs expire (typically 15 min–1 hour). A long-lived refresh token (stored in HttpOnly cookie) exchanges for a new access JWT without re-login.

⚡ Production Tips
  • Store JWTs in memory or HttpOnly cookies, never localStorage — XSS attacks can steal localStorage tokens.
  • Short access token expiry (15 min). Long refresh token in HttpOnly cookie. Rotate refresh tokens on use.
  • Use RBAC (Role-Based Access Control) for role checks, but don't forget resource-level authorization — a user with "viewer" role can't view other users' private data.
  • For OAuth ("Sign in with Google"), you're the client — Google does authentication, you receive an identity assertion. You still handle authorization.
🎯 Interview Prep
"What's the difference between 401 and 403?"
✓ Strong

"401 Unauthorized means authentication failed — 'I don't know who you are.' The client should re-authenticate. 403 Forbidden means authentication succeeded but authorization failed — 'I know who you are, but you're not allowed here.' The naming is confusingly historical; 401 should've been called Unauthenticated."

"How do JWTs work and what are their limitations?"
✓ Strong

"A JWT encodes claims in a base64 payload and signs it with a secret. The server can verify it without a DB lookup — that's the scalability win. The limitation is revocation: you can't invalidate a JWT before it expires. If a user logs out or is banned, their token is still valid until expiry. The mitigations are short TTLs (15 min) plus a token blocklist in Redis for critical revocations."

CSRF vs XSS

The two most misunderstood web security attacks

Core Concept

CSRF (Cross-Site Request Forgery): Attacker tricks your authenticated browser into making a request to your bank/app. Your browser sends cookies automatically — so the malicious request has your credentials.

XSS (Cross-Site Scripting): Attacker injects malicious JavaScript into your website. When another user loads the page, the script runs in their browser — can steal cookies, tokens, or control the page.

🎭 Analogy

CSRF is like someone sending a letter pretending to be you — to your bank, using your address, so the bank thinks it's legitimate. XSS is like someone poisoning a public notice board so every person who reads it gets infected. CSRF abuses trust in the user. XSS abuses trust in the content.

Node.jsCSRF protection + XSS prevention
// CSRF: SameSite cookie is the modern fix
res.cookie('session', token, {
  httpOnly: true,   // no JS access (also fights XSS token theft)
  secure: true,    // HTTPS only
  sameSite: 'strict' // never sent on cross-site requests ← CSRF protection
});

// Or CSRF token approach (for older browsers / APIs)
const csrf = require('csurf');
app.use(csrf());
app.get('/form', (req, res) => {
  res.render('form', { csrfToken: req.csrfToken() }); // embed in form
});

// XSS: never render raw user input — escape it
// BAD — executes any script in userName
document.getElementById('name').innerHTML = userName;

// GOOD — escapes HTML characters
document.getElementById('name').textContent = userName;

// Server-side: use helmet for CSP headers
const helmet = require('helmet');
app.use(helmet.contentSecurityPolicy({
  directives: {
    scriptSrc: ["'self'"],  // only your scripts allowed
    defaultSrc: ["'self'"]
  }
}));

Attack Comparison

Attack vectorMalicious site tricks browser into requestMalicious script injected into your site
AbusesBrowser auto-sending cookiesTrust in rendered content

⚡ Production Tips
  • Use SameSite=Strict or Lax on all session cookies — this alone defeats most CSRF attacks.
  • Use textContent not innerHTML when rendering user data in the browser.
  • Set a strict Content Security Policy (CSP) header — it's your last line of defense if XSS exists.
  • Sanitize HTML on the server if you must accept rich text input (use DOMPurify or similar).
  • Use HttpOnly on session cookies — XSS can't steal what JS can't see.
🎯 Interview Prep
"Explain CSRF and how you'd prevent it."
✓ Strong

"CSRF exploits the browser's automatic cookie behavior. If I'm logged into bank.com and visit evil.com, evil.com can trigger a request to bank.com — my browser sends the session cookie automatically. Prevention: SameSite=Strict cookies tell the browser to never send the cookie on cross-site requests. Or a CSRF token — a random value embedded in forms, verified server-side — that evil.com can't read due to same-origin policy."

Distributed Systems Basics

Multiple servers, partial failures, and why the network lies

Core Concept

When your system runs on multiple machines, failures become partial and probabilistic. A server might be slow, not dead. A packet might arrive twice. The network can partition. These are normal conditions in production, not edge cases.

The CAP Theorem states you can only guarantee two of three: Consistency (all nodes see same data), Availability (every request gets a response), Partition Tolerance (system works despite network splits). In practice, partitions happen — so you choose between C and A.

🎭 Analogy

CAP is like running a bank with branches. If the phone line between branches goes down (partition), you either (A) refuse all transactions until reconnected (Consistency) or (B) let each branch keep operating with possibly stale balances (Availability). There's no free lunch.

CP Systems

Consistent + Partition Tolerant. May refuse requests when partitioned. HBase, ZooKeeper.

AP Systems

Available + Partition Tolerant. Eventually consistent. DynamoDB, Cassandra.

Eventual Consistency

Writes propagate "eventually." Reads may be stale. Good for carts, feeds; bad for balances.

Idempotency

Same request applied twice = same result. Critical for retries. Use idempotency keys.

⚡ Production Tips
  • Design for partial failure. Any external call can fail. Use timeouts, retries, and circuit breakers.
  • Clocks drift across machines. Never compare timestamps from different servers for ordering — use logical clocks or UUIDs.
  • Include idempotency keys on all mutation operations (payments, orders). POST /payments with same key twice = one charge.
Quick Reference
CAP TheoremPick 2: Consistency, Availability, Partition Tolerance. P always happens.
Eventual consistencyWrites propagate in time. Reads may be stale briefly.
Idempotency keyClient-generated unique ID. Server deduplicates on this.

Load Balancing

Distributing traffic so no single server drowns

Core Concept

A load balancer sits in front of your servers and distributes incoming requests. It's both a traffic router and a health checker — it removes failed servers from rotation automatically.

Round Robin

Server 1, 2, 3, 1, 2, 3... Equal distribution. Simple. Ignores server load.

Least Connections

Route to server with fewest active connections. Better for variable request durations.

Sticky Sessions

Same client always hits same server. Useful for in-memory session state. Breaks horizontal scaling.

Health Checks

LB pings /health on each server. Unhealthy = removed from pool. Healthy again = re-added.

⚡ Production Tips
  • Avoid sticky sessions — they create uneven load and make horizontal scaling painful. Store session in Redis instead.
  • Health check endpoint should verify DB connectivity, not just HTTP 200. A server that can't reach the DB shouldn't receive traffic.
  • AWS ALB terminates SSL, handles health checks, and integrates with Auto Scaling — use it before rolling your own with NGINX.
Quick Reference
Round robinDistribute equally. Simple. Default in most LBs.
Least connectionsRoute to least busy. Better for uneven request durations.
Sticky session trapBreaks horizontal scaling. Use external session store instead.

Horizontal vs Vertical Scaling

Buy a bigger machine vs buy more machines
🎭 Analogy

Vertical scaling is hiring a super-employee and paying them more. Horizontal scaling is hiring more regular employees. The super-employee has limits (there's a maximum salary); hiring more people scales infinitely (in theory). But more employees mean coordination overhead (distributed systems problems).

Vertical (Scale Up)

Bigger CPU, more RAM, faster disk. Simple. Has a ceiling. Single point of failure. No code changes needed.

Horizontal (Scale Out)

More servers. Theoretically unlimited. Requires stateless architecture. Needs load balancer.

Stateless Apps

Each request carries all needed context. No server-local state. Any server can handle any request.

Auto-scaling

Cloud adds/removes servers based on CPU/memory metrics. Pay only for what you need.

⚡ Production Tips
  • Stateless services are the foundation of horizontal scaling. Move sessions, files, and caches to external stores (Redis, S3).
  • Scale vertically first if you need a quick fix. Scale horizontally for sustained growth.
  • Database is the hardest piece to scale horizontally — plan for it early (read replicas, then sharding).
Quick Reference
VerticalBigger machine. Fast to do. Has hardware ceiling.
HorizontalMore machines. Needs stateless app + load balancer.
Stateless = scalableSession in Redis, files in S3, cache in Redis. Any server, any request.

Database Replication

One writer, many readers — and what happens when the writer dies

Core Concept

Replication copies data from a primary (read/write) to one or more replicas (read-only). This serves two purposes: scale read traffic across replicas, and provide a failover target if the primary dies.

The catch: replication lag. Writes go to primary; replicas catch up asynchronously. For a few milliseconds (or more under load), a replica may serve stale data. "Read your own writes" is a common bug — user updates their profile, reads it back from a lagging replica, sees the old value.

Node.jsRoute reads to replicas, writes to primary
// Route writes to primary, reads to replicas
const primaryPool = new Pool({ host: 'primary.db', ... });
const replicaPool = new Pool({ host: 'replica.db', ... });

async function write(sql, params) {
  return primaryPool.query(sql, params);
}
async function read(sql, params, { consistent = false } = {}) {
  // For "read your own writes", use primary; otherwise replica
  const pool = consistent ? primaryPool : replicaPool;
  return pool.query(sql, params);
}
⚡ Production Tips
  • Monitor replication lag. Set alert for lag > 100ms. Lag spikes mean replicas are falling behind primary.
  • For "read your own writes" consistency, route reads to primary for a short window after a write, or use sticky routing to primary for that session.
  • Managed DBs (RDS, Cloud SQL) handle failover automatically — they promote a replica to primary and update the DNS endpoint.
Quick Reference
PrimaryAccepts writes. Source of truth.
ReplicaRead-only copy. Can serve heavy read traffic.
Replication lagReplica may serve stale data. Async replication.
FailoverPrimary dies → replica promoted. Automated in managed DBs.

Sharding / Partitioning

When one database can't hold all your data

Core Concept

Sharding splits your data across multiple database instances (shards). Each shard holds a subset of rows. A shard key determines which shard a given row lives on.

🎭 Analogy

A library with too many books for one room. You split by category: Science (shard A), History (shard B), Fiction (shard C). To find a book, you first check what category it is (shard key lookup), then go to that room. Cross-category searches are expensive — you have to check multiple rooms.

Range Sharding

user_id 1–1M → shard A, 1M–2M → shard B. Simple but hotspots possible.

Hash Sharding

shard = hash(user_id) % N. Even distribution but range queries are expensive.

Directory Sharding

Lookup table maps key to shard. Flexible but lookup table is a bottleneck.

Cross-Shard Queries

The hard part. JOINs across shards require application-level aggregation.

⚡ Production Tips
  • Sharding is complex — exhaust other options first: indexing, caching, read replicas, vertical scaling.
  • Choose shard key carefully. A bad key creates hotspots (all traffic on one shard). user_id is usually good.
  • Consider managed solutions: Amazon Aurora, Vitess (MySQL), or Citus (Postgres) that handle sharding for you.
  • Cross-shard transactions are extremely hard. Design to avoid them — shard entities together that are often queried together.
Quick Reference
Shard keyDetermines which shard. Choose for even distribution.
Hash shardingEven distribution. Bad for range scans.
Cross-shard joinApplication must fetch from multiple shards and merge. Expensive.

Optimistic Locking

Trust, verify, retry

Core Concept

Covered briefly in Chapter 1. Let's go deeper. Optimistic locking avoids holding DB locks by using a version number. You read a row (capturing the version), modify it in memory, then write back with a condition: only update if version hasn't changed. If it has — someone else edited it — your update affects 0 rows. Retry.

Node.jsOptimistic lock with retry logic
async function updateWithOptimisticLock(productId, delta, maxRetries = 3) {
  for (let attempt = 0; attempt < maxRetries; attempt++) {
    const { rows: [product] } = await db.query(
      'SELECT id, stock, version FROM products WHERE id = $1', [productId]
    );
    if (!product || product.stock + delta < 0) throw new Error('Out of stock');

    const result = await db.query(`
      UPDATE products SET stock = stock + $1, version = version + 1
      WHERE id = $2 AND version = $3
    `, [delta, productId, product.version]);

    if (result.rowCount === 1) return true; // success
    // 0 rows updated: version mismatch, retry
    await sleep(10 * (2 ** attempt)); // exponential backoff
  }
  throw new Error('Conflict after max retries');
}
Quick Reference
Version columnIncrement on every write. Acts as conflict detector.
0 rows updatedVersion mismatch = conflict. Retry with fresh read.
Best forLow-contention writes. High-contention → pessimistic is faster.

Event-Driven Architecture

Services that react to what happened, not what they were told

Core Concept

Instead of Service A directly calling Service B, A emits an event: order.created. Any interested service subscribes to this event and reacts. A doesn't know (or care) who's listening. This is extreme decoupling.

🎭 Analogy

A radio broadcast vs a phone call. A phone call (direct call) requires knowing the recipient's number and waiting for them to answer. A radio broadcast says "attention all listeners: traffic on highway 1" — anyone tuned in reacts. The broadcaster doesn't know who's listening and doesn't wait for a response.

Node.jsEvent-driven order flow
// Order service emits event
async function createOrder(orderData) {
  const order = await db.insert(orderData);
  await eventBus.publish('order.created', { orderId: order.id, ...orderData });
  return order;
  // Order service is DONE. It doesn't call inventory/email/analytics.
}

// Inventory service subscribes
eventBus.subscribe('order.created', async (event) => {
  await reserveInventory(event.productId, event.quantity);
  await eventBus.publish('inventory.reserved', { orderId: event.orderId });
});

// Email service subscribes to a different event
eventBus.subscribe('inventory.reserved', async (event) => {
  await sendConfirmationEmail(event.orderId);
});
⚡ Production Tips
  • Event sourcing: store all events as the source of truth. Current state = replay of events. Powerful for audit trails.
  • Events must be immutable and include enough context to be handled independently — don't emit "something happened" with no data.
  • Versioning events is critical. As event schemas change, consumers on old code must still work.
Quick Reference
EventImmutable fact about what happened. Past tense: order.created.
PublisherEmits event. Doesn't know or care who's listening.
SubscriberReacts to events asynchronously. Independently deployable.

Circuit Breakers

Stop trying to call a dead service

Core Concept

If Service B is failing, Service A shouldn't keep trying — it'll waste resources and slow down user requests with timeout waits. A circuit breaker monitors failures and "trips" — subsequent calls fail fast with an error instead of waiting for a timeout. After a cooldown, it tries again.

Three states: Closed (normal — calls pass through), Open (tripped — calls fail fast), Half-Open (testing — one call allowed to check if service recovered).

Node.jsCircuit breaker with opossum
import CircuitBreaker from 'opossum';

const breaker = new CircuitBreaker(callPaymentService, {
  timeout: 3000,          // fail if takes > 3s
  errorThresholdPercentage: 50, // trip if 50%+ requests fail
  resetTimeout: 30000,    // try again after 30s
  volumeThreshold: 10     // min 10 requests before tripping
});

breaker.fallback(() => ({ error: 'Payment service unavailable. Try later.' }));

breaker.on('open', () => console.warn('⚡ Circuit OPEN: payment service failing'));
breaker.on('halfOpen', () => console.log('🔍 Circuit HALF-OPEN: probing...'));
breaker.on('close', () => console.log('✅ Circuit CLOSED: service recovered'));

const result = await breaker.fire(paymentData);
Quick Reference
ClosedNormal operation. Requests pass through.
OpenToo many failures. Fail fast. No calls to downstream.
Half-OpenCooldown expired. One test call. If OK → Closed.
FallbackGraceful degradation response when circuit is Open.

Retry Strategies

Retry smarter, not harder

Core Concept

Transient failures are normal. Networks blip. Services restart. The naive fix — retry immediately — makes things worse: if a service is overloaded, hammering it with retries is a DDOS. Exponential backoff with jitter is the right answer.

Node.jsExponential backoff with jitter
async function retryWithBackoff(fn, maxRetries = 5) {
  for (let attempt = 0; attempt < maxRetries; attempt++) {
    try {
      return await fn();
    } catch (err) {
      if (attempt === maxRetries - 1) throw err; // last attempt

      // Only retry on transient errors, not 400 Bad Request etc.
      if (err.status && err.status < 500) throw err;

      const baseDelay = Math.min(1000 * 2 ** attempt, 30000); // cap at 30s
      const jitter = Math.random() * baseDelay * 0.3; // ±30% jitter
      await sleep(baseDelay + jitter);
    }
  }
}

// Delays: ~1s, ~2s, ~4s, ~8s, ~16s (with jitter)
// Jitter prevents thundering herd: 1000 clients don't all retry at t=2s
Quick Reference
Exponential backoffdelay = base * 2^attempt. Doubles each retry. Cap at max.
JitterRandom variance on delay. Prevents thundering herd problem.
Don't retry 4xx400/401/403 won't succeed on retry. Only 5xx and network errors.
Idempotency requiredRetried mutations must be safe to apply twice.

Observability

If you can't see it, you can't fix it

Core Concept

Observability is your ability to understand the internal state of your system from its external outputs. The three pillars: Logs (what happened), Metrics (how it's performing), Traces (how a request flowed through services).

Without observability, debugging production is like performing surgery blindfolded. You're guessing.

📜 Logs

Structured JSON logs. Include request ID, user ID, severity. Aggregate in Datadog/Grafana.

📊 Metrics

Counters, gauges, histograms. Request rate, error rate, latency (p50/p95/p99). Alert on anomalies.

🔍 Traces

Follow a request across services. Shows which service is slow. OpenTelemetry standard.

🚨 Alerting

Error rate spikes, latency increases, queue depth growth. PagerDuty at 3am if it's urgent.

Node.jsStructured logging with request context
import pino from 'pino';
const logger = pino({ level: 'info' });

// Middleware: attach request context to logger
app.use((req, res, next) => {
  req.log = logger.child({
    requestId: req.headers['x-request-id'] || crypto.randomUUID(),
    userId: req.user?.id,
    path: req.path,
    method: req.method
  });
  next();
});

// Usage
req.log.info({ orderId, amount }, 'Order created');
req.log.error({ err: error.message, stack: error.stack }, 'Payment failed');

// Golden signals to monitor:
// - Latency: p50, p95, p99 response times
// - Traffic: requests per second
// - Errors: 5xx error rate
// - Saturation: CPU, memory, queue depth
⚡ Production Tips
  • Log structured JSON (not strings) — machines can parse and query JSON. {"level":"error","msg":"Payment failed","userId":123} is infinitely more useful than "ERROR: Payment failed for user 123".
  • Add correlation/trace IDs to every log. When debugging, you want all logs for a single request, not searching by time.
  • Monitor the four golden signals: Latency, Traffic, Errors, Saturation. Set alerts before you need them.
  • p99 latency matters more than average. Average hides the pain of 1% of users. If p99 = 10s, 1 in 100 users waits 10 seconds.

Tier 3

Kubernetes Basics

Container orchestration at scale

Core Concept

Kubernetes (K8s) manages containers at scale — scheduling them across a cluster of machines, restarting crashed ones, scaling based on load, and routing traffic. It's the operating system for your distributed application.

Pod

Smallest deployable unit. One or more containers that share network and storage. Ephemeral by design.

Deployment

Declares desired state: "run 3 replicas of image:v2." K8s ensures this is always true.

Service

Stable DNS name + IP for a set of pods. Load balances traffic to matching pods.

Ingress

HTTP routing rules. Maps myapp.com/api → api-service. Often with cert-manager for TLS.

HPA

Horizontal Pod Autoscaler. Scale from 2 to 10 pods when CPU >70%. Automatic.

ConfigMap / Secret

Config and credentials injected as env vars or files. Never bake secrets into images.

YAMLDeployment + Service + HPA
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 3
  selector:
    matchLabels: { app: api }
  template:
    metadata:
      labels: { app: api }
    spec:
      containers:
      - name: api
        image: myrepo/api:v1.2.3   # always pin version, never :latest
        ports: [{ containerPort: 3000 }]
        readinessProbe:            # traffic only sent to ready pods
          httpGet: { path: /health, port: 3000 }
        resources:
          requests: { cpu: "100m", memory: "128Mi" }
          limits: { cpu: "500m", memory: "512Mi" }
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
spec:
  scaleTargetRef: { name: api }
  minReplicas: 2
  maxReplicas: 20
  metrics:
  - type: Resource
    resource: { name: cpu, target: { averageUtilization: 70 } }

PodSmallest unit. Ephemeral. Never reference pods directly — use Deployments.
DeploymentManages replica count and rollouts. kubectl rollout undo for rollback.
ServiceStable endpoint for pods. Internal DNS: svc-name.namespace.svc.cluster.local
Readiness probeNo traffic until /health returns 200. Critical for rolling deploys.
Resource limitsSet requests + limits. No limits = one OOM pod kills the node.

Tier 3

CI/CD

Every commit should be deployable

Core Concept

CI (Continuous Integration): Automatically build, lint, and test on every commit. Catch bugs before they merge. CD (Continuous Deployment): Automatically deploy passing commits to production. The goal: deployments so routine and automated they're not events.

GitHub ActionsFull CI/CD pipeline
name: CI/CD
on:
  push: { branches: [main] }
  pull_request: { branches: [main] }

jobs:
  test:
    runs-on: ubuntu-latest
    services:
      postgres: { image: postgres:16, env: { POSTGRES_PASSWORD: test } }
    steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-node@v4
      with: { node-version: '20', cache: 'npm' }
    - run: npm ci
    - run: npm run lint
    - run: npm run typecheck
    - run: npm test

  deploy:
    needs: test
    if: github.ref == 'refs/heads/main'   # only on main branch
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4
    - name: Build and push Docker image
      run: |
        docker build -t myrepo/api:${{ github.sha }} .
        docker push myrepo/api:${{ github.sha }}
    - name: Rolling deploy to Kubernetes
      run: |
        kubectl set image deployment/api api=myrepo/api:${{ github.sha }}
        kubectl rollout status deployment/api  # wait for rollout

Blue-Green Deploy

Two identical environments. Switch traffic from blue to green instantly. Instant rollback by switching back.

Canary Deploy

Route 5% of traffic to new version. Monitor. If good, increase to 100%. Safe for risky changes.

Feature Flags

Deploy code dark (off). Enable per user/cohort. Decouple deploy from release.

Rollback

kubectl rollout undo. Or keep previous image tagged :stable for one-command revert.

Quick Reference
CILint + test on every PR. Breaks = PR blocked. No exceptions.
CDAuto-deploy passing main branch. Trust your tests.
Blue-greenTwo live envs. Instant switch. Instant rollback. Needs 2x resources.
CanaryGradual traffic shift. Catch bugs affecting real users before full rollout.

Reverse Proxy

The gatekeeper in front of your servers

Core Concept

A reverse proxy sits between the internet and your servers. Clients talk to the proxy; the proxy forwards to the right backend. Your servers are never directly exposed. NGINX is the classic choice; Caddy is the modern, auto-SSL alternative.

NGINXReverse proxy with SSL termination and rate limiting
upstream api_servers {
  server api1:3000;
  server api2:3000;
  server api3:3000;
  keepalive 32;   # connection pool to backends
}

server {
  listen 443 ssl;
  server_name api.myapp.com;

  ssl_certificate /etc/ssl/cert.pem;
  ssl_certificate_key /etc/ssl/key.pem;

  # Rate limiting (reference to zone defined outside)
  limit_req zone=api_limit burst=20 nodelay;

  # Compression
  gzip on;
  gzip_types application/json text/html;

  location /api/ {
    proxy_pass http://api_servers;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_connect_timeout 5s;
    proxy_read_timeout 30s;
  }

  location /static/ {
    root /var/www;
    expires 1y;        # cache static assets heavily
    add_header Cache-Control "public, immutable";
  }
}
Quick Reference
SSL terminationHTTPS to the proxy, HTTP to backend. Proxy handles certs.
X-Real-IP headerPass original client IP to backend. Without this, all requests look like they come from the proxy.
UpstreamPool of backend servers. NGINX load balances across them.
TimeoutsSet proxy_read_timeout. Don't let hanging backends hold NGINX workers.

API Design

APIs are forever — design them like they are

Core Concept

Good API design is about predictability, consistency, and longevity. Once an API is public, you can't easily change it — clients depend on it. Design as if v1 will live forever.

REST + Node.jsProduction API patterns
// Versioning in URL path
app.use('/v1', v1Router);
app.use('/v2', v2Router);

// Pagination — cursor-based is better than offset for large datasets
// Offset: page 3 can change as items are added. Cursor: stable.
app.get('/v1/orders', async (req, res) => {
  const { cursor, limit = 20 } = req.query;
  const orders = await db.query(`
    SELECT * FROM orders
    WHERE id > $1
    ORDER BY id ASC LIMIT $2
  `, [cursor || 0, parseInt(limit) + 1]);

  const hasMore = orders.length > limit;
  res.json({
    data: orders.slice(0, limit),
    nextCursor: hasMore ? orders[limit - 1].id : null,
    hasMore
  });
});

// Idempotency key for POST mutations
app.post('/v1/payments', async (req, res) => {
  const idempotencyKey = req.headers['idempotency-key'];
  if (!idempotencyKey) return res.status(400).json({ error: 'Idempotency-Key required' });

  // Check if already processed
  const existing = await redis.get(`idem:${idempotencyKey}`);
  if (existing) return res.json(JSON.parse(existing));

  const payment = await processPayment(req.body);
  await redis.setex(`idem:${idempotencyKey}`, 86400, JSON.stringify(payment));
  res.json(payment);
});

⚡ Production Tips
  • Use cursor-based pagination over offset. Offset pagination on page 500 reads and discards 10,000 rows.
  • Return consistent error shapes: {"error": "message", "code": "PAYMENT_FAILED", "details": {...}}
  • Document with OpenAPI/Swagger. Generate client SDKs from it.
  • Require idempotency keys on all non-safe (POST/PUT/DELETE) endpoints that cause side effects.
🎯 Interview Prep
"How would you design a pagination API for a large dataset?"
✓ Strong

"I'd use cursor-based pagination over offset. Offset has two problems: it's slow on deep pages (SELECT * LIMIT 20 OFFSET 100000 still reads 100,020 rows) and it's unstable — if a new item is inserted, page 2 now has a different result. Cursor-based uses a stable ID: WHERE id > :cursor ORDER BY id LIMIT 20. The client passes the last seen ID as the next cursor. O(log n) with an index, stable results, works fine at any depth."
