System Design Interview Notes

Use this page to master the system design round. Covers the 6-step framework, capacity estimation, core building blocks, classic distributed system problems, and how to present your own projects (Eudoro, Gaza40+, DataSync) as system design answers.

01
Methodology

The 6-Step Interview Framework

Never jump straight to the architecture diagram. Control the pace.
1. Requirements (3-5 min): Clarify functional (what it does) and non-functional (scale, latency, CAP theorem trade-offs). Ask questions.
2. Capacity Estimation (3-5 min): Back-of-the-envelope math. DAU, QPS, storage, bandwidth. Keep it simple (10^5, 10^6).
3. API Design (3-5 min): Define endpoints, HTTP methods, request/response JSON payload shape.
4. Data Model (3-5 min): SQL vs NoSQL. Tables, primary keys, foreign keys, partition keys.
5. High-Level Design (10-15 min): Draw the boxes. Client -> LB -> App Servers -> DB/Cache. Satisfy the happy path.
6. Deep Dive & Bottlenecks (10 min): Address scaling limits, single points of failure, edge cases, and specific interviewer probes.
02
Math

Capacity Estimation (Back-of-Envelope)

Show you understand scale magnitude. Don't stress exact numbers.

Daily Active Users (DAU)

Determine total users, DAU, and requests per user per day.
Ex: 10M DAU * 10 req/day = 100M req/day.

QPS (Queries Per Second)

Divide daily requests by 10^5 (approx seconds in a day: 86,400).
Ex: 100M / 10^5 = 1,000 QPS. Peak QPS = 2x or 3x average.

Storage

Size per object * objects per day * 5 years.
Ex: 10M text posts/day * 1KB = 10GB/day. 3.6TB/year. 18TB for 5 years.

Bandwidth

Ingress: Writes/sec * size. Egress: Reads/sec * size.
Ex: 100 writes/sec * 1MB = 100MB/s ingress bandwidth.

Patterns

Classic Problems

Core architectures that are repeated in interviews.

URL Shortener

Core: Map long URL to short 7-char hash (Base62).
DB: Relational or NoSQL. Key-Value is fine.
Bottleneck: Reads heavily outweigh writes. Add Redis cache.

Chat System (WhatsApp)

Core: Real-time bi-directional messaging.
Protocol: WebSockets.
Architecture: Chat servers, presence servers, push notifications, message sync queues.

Rate Limiter

Core: Prevent abuse.
Algorithms: Token bucket, Leaky bucket, Sliding window.
Storage: Redis (fast reads/writes, atomic operations via Lua scripts).

News Feed

Core: Aggregate content from followed users.
Pattern: Fan-out on write (push model for normal users), Fan-out on read (pull model for celebrities). Cache heavy.

05
Decisions

Trade-offs

Every architecture decision has a cost. Be ready to discuss it.
SQL vs NoSQL: Relational data with ACID guarantees vs Flexible schema, horizontal scaling, key-value lookups.
Consistency vs Availability (CAP): In a partition (P), do you want the latest data (C - might error out) or *any* data (A - might be stale)?
Monolith vs Microservices: Fast initial dev, simple deployment vs independent scaling, fault isolation, tech diversity (but high operational overhead).
Sync vs Async: Real-time response but blocks thread vs fast initial response, processing in background (queues), requires polling/webhooks.

Deep Reference

The numbers and definitions worth having loaded before the interview, not derived during it.

Everything above is reasoning you build in the room. This section is the opposite: facts you should be able to state without working them out, because time spent deriving them is time not spent on the design.

Latency, by order of magnitude

Do not memorize exact figures — hardware moves and precision is not the point. Memorize the ratios, because the whole value of these numbers is knowing what dominates.

OperationRough timeWhat it implies
L1 / L2 cache reference~1 nsFree, relative to anything below.
Main memory reference~100 ns~100× cache. Why data locality matters in hot loops.
SSD random read~100 µs~1,000× memory. Why an in-memory cache in front of a database is worth having.
Network round trip, same datacenter~0.5 msCheap enough that a service call is fine; not so cheap that 50 of them are.
Disk seek (spinning)~10 msThe reason B-trees are shaped the way they are.
Round trip across continents~150 msBounded by the speed of light. No amount of optimization fixes it — only moving the data closer, which is what a CDN is.
The one that changes designs

A cross-continental round trip is roughly 150 ms and cannot be optimized away, because it is physics rather than software. That single fact justifies CDNs, edge caching, regional replicas, and why a chatty client-server protocol that is fine in a datacenter is unusable over the public internet. If you remember one number, remember this one and what it forces.

Capacity arithmetic

Estimation questions are testing whether you can keep the units straight under mild pressure, not whether you are right. Round aggressively and say you are rounding.

FactValue
Seconds in a day86,400 — call it 100k
1 million writes/day~12 writes/second average
Peak versus averageAssume 2–3× average; say which you are using
Bytes: KB → MB → GB → TB×1,000 each (use decimal, it is faster and close enough)
A row of typical metadata~1 KB unless it holds text or blobs
1M rows × 1 KB~1 GB — the anchor most storage estimates hang off
Read:write ratio, consumer appsOften 100:1 or higher. State your assumption, it drives everything.

Consistency vocabulary

TermMeaning
Strong consistencyEvery read returns the most recent write. Costs coordination, and therefore latency.
Eventual consistencyReplicas converge if writes stop. Says nothing about how long, which is why "eventual" needs a number attached in practice.
Read-your-writesA user always sees their own last write. Much weaker than strong consistency and usually what the product actually needs.
Monotonic readsTime never appears to run backwards for one reader. Prevents the "my comment disappeared then came back" bug.
QuorumWith R + W > N, a read set and a write set must overlap, so a read is guaranteed to see the latest write.
CAPUnder a network partition, choose consistency or availability. It says nothing about the normal case, which is where the misuse comes from.
PACELCThe honest extension: under Partition, A or C; Else, Latency or Consistency. Covers the 99% of the time when nothing is partitioned.

Pattern index

Idempotency key

Client-supplied unique id, stored with its result. Makes retries safe. Reach for it whenever a network can retry a non-idempotent action.

Outbox

Write the domain change and the event to publish in one local transaction; a relay publishes from that table. Removes the "saved but never published" gap between a database and a broker.

Saga

A long-running workflow as a series of local transactions with compensating actions. What replaces distributed transactions once data spans services.

Circuit breaker

After repeated failures, stop calling a dependency for a while. Stops one slow service from consuming every thread in its callers — the mechanism behind most cascading failures.

Backpressure

Bound your queues. An unbounded queue converts an overload into an out-of-memory crash and hides the problem until it is fatal.

Cache-aside

Read cache, miss, read database, populate. The default. Its hard part is invalidation, and its failure mode is the stampede when a hot key expires.

Bloom filter

Probabilistic set membership: definitely-not-present or maybe-present, in very little memory. Skips pointless lookups for keys that do not exist.

Consistent hashing

Maps keys to nodes so that adding or removing one moves only a small fraction of keys, instead of remapping everything.

Closing checklist

In the last minutes, these are the dimensions that separate a complete answer from a diagram. Naming even two of them unprompted reads as production experience.

✓ What happens when this component dies? Where is the single point of failure?
✓ What is the hot key or hot partition, and what happens when it appears?
✓ Which operations must be idempotent, given that every network call can be retried?
✓ What do I measure, and what would page someone at 3am?
✓ How does this behave at 10× the traffic? What breaks first?
✓ Where does data live, who may read it, and how long is it kept?
✓ How does it get deployed and rolled back without downtime?
