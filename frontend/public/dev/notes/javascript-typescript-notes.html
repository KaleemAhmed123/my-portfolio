Internals

Execution Model

How JS runs under the hood.

Event Loop

JS is single-threaded. The event loop continuously checks if the Call Stack is empty. If it is, it pushes tasks from the Task Queues to the stack.

Micro vs Macrotasks

Microtasks: Promises (.then), process.nextTick, queueMicrotask. Higher priority.
Macrotasks: setTimeout, setInterval, setImmediate, I/O.

process.nextTick

Node.js specific. Evaluated *before* the next event loop tick and before microtasks. Can cause starvation if used recursively.

Scope

Closures & Scope

Functions remembering where they were born.

Lexical Scope

A function's scope is determined by where it is physically written in the code, not where it is called.

Closure

A closure is a function bundled together with references to its surrounding state (lexical environment). It gives you access to an outer function's scope from an inner function, even after the outer function has returned. Used for data privacy and currying.

Closure Example (Data Privacy)
function createCounter() {
  let count = 0; // private variable
  return function() {
    count++;
    return count;
  };
}
const counter = createCounter();
console.log(counter()); // 1
console.log(counter()); // 2
03
Objects

Prototypes & Classes

There is one mechanism here. Everything else is syntax on top of it.

JavaScript has no classes in the way C++ or Java has classes, and understanding that properly makes every confusing thing in this area stop being confusing. What it has is one rule: every object holds a hidden link to another object, and a failed property lookup follows that link. That is the entire mechanism. Inheritance, methods, class, new, and instanceof are all built out of it.

When you write user.save(), the engine looks for save on user itself. If it is not there, it follows the hidden link — the object's [[Prototype]] — and looks there. Then it follows that object's link. It continues until it finds the property or reaches an object whose link is null, at which point the answer is undefined. That path is the prototype chain, and it is walked on every property access.

The distinction that trips everyone up

__proto__ (properly Object.getPrototypeOf(obj)) is the link an object uses for lookups. .prototype is a property that exists only on functions, and it is not that function's own prototype — it is the object that will be assigned as [[Prototype]] to instances the function creates with new. One is what an object inherits from; the other is what a constructor hands out. They are different objects and the names are genuinely misleading.

What new actually does

Four steps, and being able to list them is a common interview question because it demystifies the whole model:

new Foo(args), written outjs
// 1. Create a fresh empty object.
const obj = {};
// 2. Link it to the constructor's .prototype object.
Object.setPrototypeOf(obj, Foo.prototype);
// 3. Call the constructor with `this` bound to the new object.
const result = Foo.apply(obj, args);
// 4. Return that object -- unless the constructor returned its own object.
return (typeof result === 'object' && result !== null) ? result : obj;

Step 2 is why methods defined on Foo.prototype are shared: a thousand instances do not each get a copy of the method, they each hold a link to the one object that has it. That is a real memory property, not a detail — it is the reason methods go on the prototype and per-instance data goes on the instance.

class is sugar, with two real differences

A class declaration produces a function whose .prototype carries the methods — exactly what people wrote by hand before 2015. extends sets up the chain between the two prototype objects, and super() calls the parent constructor with the current this. If you can explain class in terms of the prototype chain, you have understood it.

Two things are not merely sugar and are worth knowing. Class bodies run in strict mode always. And class declarations are hoisted but stay in the temporal dead zone, so unlike a function declaration you cannot use one before it appears — a subtle difference that produces a ReferenceError rather than the undefined people expect.

this is decided at call time

The other half of the confusion in this area. In a normal function, this is not determined by where the function was written but by how it was called. Resolve it with this order:

Call shapethis is
new Foo()The newly created object.
fn.call(x) / .apply(x) / .bind(x)Explicitly x.
obj.method()obj — whatever is left of the dot, at the moment of the call.
fn()undefined in strict mode; the global object otherwise.
Arrow functionNone of the above. Arrows have no this of their own; they close over the one from the enclosing scope, permanently.

This is the source of the classic bug: const save = user.save; save() loses the receiver, because this was never attached to the function — it came from the dot. It is also why arrow functions fixed so much callback pain, and why an arrow is the wrong choice for an object method that needs this.

Analogy

The prototype chain is asking a question up a chain of desks. You ask your own desk first; if the answer is not there you pass it to the desk behind, and so on until someone answers or you run out of desks. Classical inheritance stamps a copy of the rulebook onto every desk. JavaScript hands every desk a pointer to the same rulebook — which is why changing that shared object is visible to everyone at once.

"How does inheritance work in JavaScript?"

"Through delegation rather than copying. Every object has a hidden link to another object, and when a property is not found on the object itself the engine follows that link and keeps following it until it finds the property or hits null. class and extends are syntax over exactly that — a class's methods live on one shared prototype object and instances link to it, which is why a thousand instances do not carry a thousand copies of a method. The distinction I would flag is between .prototype, which only functions have and which describes what their instances will link to, and an object's actual [[Prototype]], which is the link it uses for lookups. Those two names sound like the same thing and are not."

Types

TypeScript Depth

Beyond basic interfaces.

Generics

Reusable components that work over a variety of types rather than a single one. function identity<T>(arg: T): T

Utility Types

Partial<T>, Pick<T, K>, Omit<T, K>, Record<K, T>. Used heavily in React props and API responses.

Discriminated Unions

Using a common literal property (like type: 'success' | 'error') to narrow down a union type in a switch statement safely.

satisfies Operator

Validates that an object matches a type *without* widening its specific literal types. const routes = { home: '/' } satisfies Record<string, string>

Depth

Advanced Concepts

The features you reach for rarely, and should be able to explain when you do.

Iterators and generators

Start with the protocol, because the syntax makes no sense without it. Anything is iterable if it has a method at the key Symbol.iterator that returns an object with a next() method, and next() returns { value, done }. That is all for...of, spread, and destructuring know how to do — they call next() until done is true. Arrays, strings, Map and Set implement it; plain objects do not, which is precisely why for...of works on an array and throws on an object.

A generator is a function that builds that protocol for you. function* returns an object satisfying the iterator protocol, and yield suspends execution — with the local variables intact — until the next next() call resumes it. The property that makes generators genuinely useful is laziness: values are produced on demand, so a sequence can be infinite, or can pull pages from an API only as far as the consumer actually reads.

lazy pagination without loading everythingjs
async function* allUsers() {
  let cursor = null;
  do {
    const page = await fetchPage(cursor);
    yield* page.items;   // hand out one item at a time
    cursor = page.next;
  } while (cursor);
}

// Stops after 10 -- later pages are never requested.
let n = 0;
for await (const user of allUsers()) {
  if (++n > 10) break;
}

Symbols

A Symbol is a primitive whose only property is that it is unique — two symbols with the same description are still different keys. That makes them useful for metadata you want to attach to an object without colliding with real keys or showing up in Object.keys() and JSON.stringify. The well-known symbols are the interesting ones: Symbol.iterator makes your object work with for...of, Symbol.asyncIterator with for await. They are the hooks the language uses to let your objects participate in built-in syntax.

Proxy and Reflect

A Proxy wraps an object and intercepts the fundamental operations performed on it — property reads, writes, deletion, in checks. This is how reactivity systems know a value was read: Vue 3's reactivity and several ORMs are built on it. Reflect provides the default implementations, so a trap can do its own work and then forward to normal behaviour rather than reimplementing it.

a trap that forwardsjs
const tracked = new Proxy(target, {
  get(obj, key, receiver) {
    track(key);                                // the extra behaviour
    return Reflect.get(obj, key, receiver);   // then the normal one
  }
});

WeakMap and memory

A normal Map holds a strong reference to its keys, so an object used as a key can never be garbage collected while the map lives — a genuine leak if the map is long-lived and the keys are DOM nodes or request objects. A WeakMap holds its keys weakly: if nothing else references the key, the entry disappears. The trade is that a WeakMap is not enumerable — you cannot list its contents, because what it contains can change whenever the collector runs. It is the right structure for associating private data with an object you do not own.

Modules: ESM and CommonJS

The difference that causes real problems is not syntax, it is timing. CommonJS require() is synchronous and resolved at runtime, so you can call it conditionally inside a function. ESM import is resolved statically before any code executes, which is what makes tree-shaking possible — a bundler can see which exports are unused because the graph is knowable without running anything. It is also why import cannot be placed inside an if, and why await import() exists for the cases where you genuinely need a runtime decision.

The second practical difference: CommonJS exports a value, ESM exports a live binding. If a module reassigns an exported variable later, an ESM importer sees the new value and a CommonJS importer keeps the old one.

"When would you use a generator?"

"When the consumer should control how much work happens. The property that makes generators worth reaching for is laziness — execution suspends at each yield with the local state intact, so nothing is computed until someone asks for the next value. The case I find genuinely useful is paginating an API: an async generator can expose a flat stream of items while only fetching the next page when the consumer actually reads that far, so a caller that breaks after ten items never triggers the later requests. Without it you either load everything up front or leak pagination handling into every call site."

Interview

Tricky Questions

The classic "what does this output" questions.
"What is the difference between == and ===?"

== performs type coercion before comparison (e.g., '1' == 1 is true). === checks both value and type without coercion (strict equality). Always use === unless specifically checking for null/undefined simultaneously (x == null).

"How does this work in JavaScript?"

In standard functions, this is determined by *how* the function is called (the object left of the dot). In arrow functions, this is lexically bound (it inherits this from the surrounding scope at the time of definition). bind(), call(), and apply() can explicitly set this.
