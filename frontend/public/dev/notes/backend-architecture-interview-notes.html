01
Runtime

Node.js and Express fundamentals

You should explain why Node works well for I/O-heavy APIs.

Event Loop

Single JS thread coordinates async I/O. CPU-heavy work blocks the loop unless moved to worker threads or external services.

Middleware Chain

Express middleware handles parsing, auth, validation, request IDs, logging, error mapping, and rate limits.

Error Handling

Use centralized error middleware, typed errors, consistent response shape, and no stack traces in production responses.

TypeScript

Use DTOs, service interfaces, typed request context, and validation at runtime with Zod/Joi because TS disappears at runtime.

"Why use Node.js for backend services?"

Strong answer: "Node is efficient for I/O-heavy workloads like API gateways, commerce flows, queue producers, and integrations because async I/O lets one process handle many concurrent sockets. I would avoid CPU-heavy OCR or PDF processing inside the request path; that belongs in a worker or external service."

Wallet correctness rule

Money-like systems need immutable ledger entries, idempotency keys, transaction boundaries, audit logs, and reconciliation. Never trust only a mutable balance column without an audit trail.

"How do you prevent duplicate work in RabbitMQ?"

Strong answer: "Consumers must be idempotent. I store a processed event ID or use a natural idempotency key, perform the DB update in a transaction, and ack only after commit. Retries use backoff and after max attempts the message goes to a DLQ with enough context to debug."

05
Security

JWT, OAuth, RBAC, and tenant safety

Authentication identifies; authorization decides.

JWT

Validate signature, issuer, audience, expiry. Do not put secrets in payload. Support token revocation for logout/security events.

Google OAuth

OAuth proves identity through provider. Your app still creates users, sessions, roles, tenants, and authorization rules.

RBAC

Roles map to permissions. Enforce server-side on every route and data query, not only in frontend navigation.

Multi-tenancy

Every query must scope by tenant/org. Add indexes on tenant_id and test cross-tenant access denial.

07
Deep Reference

Backend project-building and interview reference

Use this section when you need implementation-level recall.

What a senior interviewer is really testing

They are not only asking whether you know Node, Redis, RabbitMQ, or Prisma. They are checking whether you can predict failure modes: duplicate requests, slow DB queries, stuck workers, race conditions, leaked permissions, partial external API failures, bad deploys, and poor observability. Every answer should mention correctness first, then scale, then operations.

Node.js request lifecycle

A typical request flows through the reverse proxy, Express middleware, auth, validation, controller, service layer, repository/database calls, response mapping, and centralized error handling.

  • Middleware: attach request ID, parse JSON, validate content type, authenticate token, apply rate limit, log request start/end.
  • Controller: HTTP-specific code only. Read params/body/query, call service, map result to status code.
  • Service: business rules. Transactions, authorization decisions, idempotency, workflow orchestration.
  • Repository: database queries. Keep SQL/Prisma details away from controllers.
  • Error handler: convert domain errors into stable API error responses.

Event loop and performance

Node handles many concurrent I/O operations well, but the JS thread still runs one piece of JS at a time. Heavy CPU work blocks all requests in that process.

  • Good fit: REST APIs, API gateways, queue producers/consumers, integrations, websockets.
  • Risky inside request path: image processing, PDF generation, OCR, huge JSON parsing, encryption-heavy loops, complex report generation.
  • Fixes: worker threads, child processes, background jobs, streaming, pagination, moving CPU work to Python/service/lambda.

MS
Microservices

Microservices without hand-waving

A 12-service claim must be backed by boundaries and tradeoffs.

When microservices are justified

Use microservices when different domains need independent deployability, scaling, ownership, or reliability boundaries. Do not split only because it sounds senior.

  • Good split: order, payment, wallet, shipment, notification, catalog, seller/admin.
  • Bad split: tiny CRUD services that always change together and share the same database tables.
  • Cost: distributed tracing, deployments, data consistency, contract testing, network failures.

Sync vs async communication

Use synchronous HTTP when the caller needs an immediate answer. Use events/queues when work can happen after durable acceptance.

  • Sync: login, product details, checkout validation, admin reads.
  • Async: send email, update seller wallet, create shipment, push notification, index search.
  • Rule: user-facing command should complete after the minimum durable state change, not after every downstream side effect.

Data ownership

Each service should own its database or at least its schema boundary. Other services ask through API/events, not direct table reads.

  • Direct DB sharing creates hidden coupling and unsafe deploys.
  • Read models can be duplicated asynchronously when dashboards need aggregated data.
  • Use outbox/inbox patterns when events must reflect committed DB changes.

MQ
RabbitMQ

Message queue implementation model

At-least-once delivery means duplicates are normal.
Producer validates command and commits local DB state. If event correctness matters, it writes to an outbox table in the same transaction.
Publisher sends event to RabbitMQ exchange with message ID, event type, aggregate ID, timestamp, trace ID, and payload version.
Queue routes event to one or more consumers. Consumers process with prefetch limits so one worker does not reserve unlimited messages.
Consumer checks idempotency. If already processed, it acks and exits. Otherwise it performs work and commits its own DB transaction.
On transient failure, message is retried with delay/backoff. After max attempts, it goes to DLQ with error context for manual or automated recovery.
"Does RabbitMQ guarantee exactly-once processing?"

No. In practical systems, assume at-least-once delivery. A message can be redelivered if the consumer crashes after doing work but before acking. Exactly-once business behavior comes from idempotent consumers, unique constraints, processed-message tables, and state machines.

SEC
Security

Auth, RBAC, and tenant isolation checklist

Security bugs are usually missing checks at one boundary.
Authentication: verify JWT signature, expiry, issuer, audience, and token revocation when needed.
Authorization: check permission on the server for every action. UI hiding is not authorization.
Tenant scoping: every query includes organization_id/tenant_id; test cross-tenant denial.
RBAC model: roles are shortcuts for permissions; permissions should describe actions such as order.refund.
Audit logs: record sensitive actions: payout approval, role changes, refund, document verification, manual data correction.
Input validation: validate body/query/params at API boundary; never trust client-calculated price, role, tenant, or amount.
ANS
Interview Answers

Backend answers worth memorizing

Use these as patterns, not scripts.
"How would you debug a slow API?"

I would start with metrics to confirm which endpoint and percentile is slow, then inspect traces/logs for where time is spent: app CPU, DB query, Redis, external API, queue wait, or network. If DB is slow, I run EXPLAIN ANALYZE and check indexes/query shape. If dependency is slow, I check timeouts, retries, and circuit breakers. I would avoid adding cache until I know the bottleneck and invalidation behavior.

"How would you design a rate limiter?"

For distributed APIs, use Redis so all app instances share counters. For simple protection, fixed window or sliding window counters may work. For smoother traffic, use token bucket or leaky bucket. Choose key by IP, user ID, API key, or route. Return 429 with retry-after, and monitor limited request counts so legitimate users are not blocked by bad thresholds.

"How do you make an API idempotent?"

The client sends an idempotency key per logical operation. The server stores that key with request hash, status, and response. If the same key arrives again, it returns the original result instead of repeating side effects. For payments/orders, the idempotency record and business write should be in the same transaction or protected by a unique constraint.
