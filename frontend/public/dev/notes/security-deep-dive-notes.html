Foundation

OWASP Top 10

Not a checklist. A ranked list of the root causes that keep showing up.

Start with what the list actually is, because interviewers ask that before they ask you to recite it. OWASP is a nonprofit that periodically analyses breach and vulnerability data across thousands of real applications, groups what it finds by root cause, and ranks the categories by how often they appear and how badly they hurt. The Top 10 is the output of that exercise. It is a description of where software keeps failing, not a specification you can be compliant with.

Two consequences follow, and both are worth saying out loud in an interview. First, the categories are broad on purpose — "Broken Access Control" covers a missing if statement and a mis-scoped S3 bucket alike, because the underlying mistake is the same. Second, the list is revised every few years as the data shifts. The edition below is the widely-cited 2021 revision; the ordering moves between editions, so quote the reasoning rather than the rank number.

The single idea underneath the whole list

Almost every entry is a trust boundary that someone forgot was a boundary. Data crosses from a place you do not control into a place you do — a request body, a URL, a header, a dependency, a container image — and somewhere on that path it stops being treated as hostile. Injection, SSRF, deserialization, and supply-chain attacks are all that one mistake wearing different clothes. If you can only remember one thing, remember to ask "where does untrusted input stop being treated as untrusted?"

The 2021 list, mechanism first

#CategoryWhat actually goes wrong
A01Broken Access ControlThe server authenticates the user, then trusts the client about what that user may do. Changing an id in a URL returns someone else's record. This is number one because authorization is per-endpoint work and there is no framework that does it for you.
A02Cryptographic FailuresSensitive data is stored or moved without adequate protection — plaintext at rest, a homemade cipher, an unsalted or fast hash, TLS terminated somewhere and then carried onward in the clear.
A03InjectionInput is concatenated into something an interpreter parses — SQL, a shell, an LDAP filter, a template. The interpreter cannot tell your intent from the attacker's because by the time it sees the string, both look identical. Covered in section 02.
A04Insecure DesignThe code correctly implements a design that was never safe: no rate limit on a password reset, a business flow that can be replayed, a trust assumption that does not hold. No amount of careful implementation fixes it.
A05Security MisconfigurationDefaults left in place. Debug endpoints in production, verbose stack traces, a permissive CORS policy, an admin account with the shipped password, cloud storage that is public because public was easier.
A06Vulnerable & Outdated ComponentsYou did not write the vulnerability, you installed it. A modern service is mostly other people's code, and that code has a CVE feed.
A07Identification & Authentication FailuresCredential stuffing that works because there is no throttling, sessions that never expire, tokens that survive a logout, password reset flows that leak whether an account exists.
A08Software & Data Integrity FailuresTrusting code or data whose provenance you never checked — an unsigned update, a CI pipeline anyone can write to, deserializing an object graph an attacker supplied.
A09Logging & Monitoring FailuresNot an attack, an amplifier. It is why the average breach is discovered months after it starts, usually by someone outside the company.
A10Server-Side Request ForgeryYour server fetches a URL the user chose. The server sits inside the network perimeter, so it can reach things the attacker cannot. Covered in section 02.

Why A01 sits at the top

It is worth understanding this one properly, because it is the category most likely to appear in your own code. Authentication answers "who is this?" and is solved once, centrally, usually by a library. Authorization answers "may this person do this specific thing to this specific record?" — and that question has a different answer at every endpoint. There is no central place to solve it, so it gets solved N times, and the N+1th endpoint is the one that ships without the check.

The classic shape is the insecure direct object reference: GET /api/invoices/1043. The handler looks up invoice 1043 and returns it. It verified that you are a logged-in user; it never verified that invoice 1043 is yours. The fix is not to obfuscate the id — UUIDs make guessing harder but change nothing about the missing check. The fix is to scope every query by the authenticated principal, so that ownership is a property of the lookup rather than a separate if someone can forget:

the shape of the fixpseudo
// Fragile: two statements, and the second one can be forgotten.
const invoice = await db.invoice.findUnique({ where: { id } });
if (invoice.ownerId !== user.id) throw forbidden();

// Durable: ownership is part of the query. A miss is a 404, not a leak.
const invoice = await db.invoice.findFirst({
  where: { id, ownerId: user.id }
});
Analogy

Authentication is the guard checking your ID at the building entrance. Authorization is whether your badge opens this door. Broken access control is a building where the front desk is immaculate and every internal door is unlocked, because the doors were installed by different teams and only some of them remembered.

"Walk me through the OWASP Top 10."

"I would not recite it as ten items, because it is not ten problems — it is mostly one problem seen from ten angles. Untrusted data crosses a boundary and stops being treated as untrusted. Injection is that at an interpreter, SSRF is that at an outbound request, deserialization is that at an object graph, supply chain is that at build time. The two entries that do not fit that pattern are broken access control, which is authorization being per-endpoint work with no central place to enforce it, and logging failures, which is not an attack at all but the reason attacks run undetected for months. If you want me to go deeper on any one of them I would pick access control, since it is the one I have had to design for directly."

02
Attacks

Injection & SSRF

When user input breaks out of its context.

SQL Injection

Attacker sends input that modifies the SQL query logic.
Fix: Always use Parameterized Queries (Prepared Statements) or an ORM like Prisma. Never concatenate strings for SQL.

NoSQL Injection

Passing an object instead of a string to a MongoDB query (e.g., {"$ne": null}).
Fix: Sanitize inputs, enforce types (TypeScript + Zod validation before DB queries).

Command Injection

Unsanitized input passed to child_process.exec.
Fix: Use execFile or spawn instead of exec, passing arguments as an array so they aren't parsed by the shell.

SSRF (Server-Side Request Forgery)

Tricking your server into making an HTTP request to an internal IP (like AWS Metadata API 169.254.169.254).
Fix: Restrict outbound URLs, validate domains, run isolated workers.

03
Browser

XSS & CSRF

Protecting the client from malicious payloads.

XSS (Cross-Site Scripting)

Attacker injects malicious JS into the page (Stored, Reflected, or DOM-based). That JS can then steal localStorage tokens or make actions on behalf of the user.
Mitigation: Escape output (React does this automatically). Never use dangerouslySetInnerHTML without a sanitizer like DOMPurify. Use HttpOnly cookies for tokens so JS can't read them. Set CSP (Content Security Policy) headers.

CSRF (Cross-Site Request Forgery)

Attacker tricks a victim's browser into making an authenticated request to a vulnerable site (using the browser's automatic cookie inclusion).
Mitigation: Use SameSite=Lax or Strict on cookies. If supporting older browsers, use Anti-CSRF tokens (Synchronizer Token Pattern). Or require a custom header (e.g., X-Requested-With) which triggers a CORS preflight that blocks the attack from third-party domains.

05
Policy

CORS (Cross-Origin Resource Sharing)

The most misunderstood security feature.
"Why does CORS exist, and how does a Preflight work?"

"The Same-Origin Policy prevents a malicious site from reading data from another site. CORS allows a server to explicitly whitelist origins. For complex requests (like POST with application/json), the browser first sends an OPTIONS (Preflight) request. The server replies with Access-Control-Allow-Origin and Access-Control-Allow-Headers. Only if that passes does the browser send the actual request. CORS protects the *client*, not the server—Postman bypasses CORS entirely."

Platform

Infra Security

The attack surface that exists whether or not your application code is perfect.

Everything so far has been about code you wrote. This section is about the parts an attacker reaches without touching your handlers at all: the secrets, the transport, the host, the pipeline, and the dependencies. These fail differently from application bugs. An injection flaw needs someone to find and exploit it; a public S3 bucket or a leaked key needs someone to simply notice, and automated scanners notice within minutes.

Secrets

The mental model that matters: a secret is not a value, it is a value plus a blast radius plus a rotation story. When you ask "where should this live?", you are really asking "who can read it, and what happens the day it leaks?"

Never in the repo

Git is append-only. Deleting a committed key in a later commit does not remove it — it stays in history, in every clone, and in every fork. A key that has been pushed is burned; the only real remediation is rotation, not deletion.

Environment, not code

Config comes from the environment so the same artifact can run in staging and production. Watch the client boundary though: any bundler that inlines variables into a browser bundle — VITE_*, NEXT_PUBLIC_* — is publishing them, whatever the file is named.

Managed stores for anything real

AWS Secrets Manager, SSM Parameter Store, Vault. What you buy is not encryption, it is rotation and an audit trail: you can answer who read the value and when, and you can change it without a redeploy.

Least privilege on the credential

The database user your API connects as should not be able to DROP TABLE. Scope the IAM role to the specific bucket and the specific actions. Most breach severity comes from over-permissioned credentials, not from the initial foothold.

Transport

TLS gives you three properties, and it is worth separating them because interviewers probe the difference: confidentiality (an observer cannot read the traffic), integrity (an observer cannot alter it undetected), and authenticity (you are talking to the host you think you are, because a CA vouched for the certificate). Encryption alone gives you the first two; the certificate chain is what gives you the third, and it is the one that stops an active man-in-the-middle rather than a passive listener.

Two practical failure modes. The first is terminating TLS at a load balancer and then speaking plain HTTP to the service behind it — fine if that hop is a trusted network you control, a real exposure if it crosses a shared one. The second is redirecting HTTP to HTTPS without Strict-Transport-Security: the very first request still goes out in the clear, which is the window an attacker on the same network needs. HSTS tells the browser never to try plaintext for this host again.

Why CSP is worth the effort

Every other XSS defence is a promise that you escaped output correctly everywhere, forever, including in the code someone adds next quarter. CSP is a different kind of control: it assumes you will eventually fail and removes the attacker's payoff anyway, because injected script has no permitted origin to execute from. Defence in depth means pairing a control that prevents the bug with one that survives the bug.

Host and container

Run as a non-root user — container escape is rarer than people fear, but a process running as root inside a container that has a mounted host path is a much shorter path to the host than one running as uid 1000. Keep base images small: alpine or a distroless base has fewer packages, which means a smaller CVE surface and less for an attacker to pivot with once inside. Do not bake secrets into image layers; anyone who can pull the image can read them, deleted in a later layer or not — the same append-only trap as Git.

Supply chain

Most of what runs in production is code you did not write. npm audit and Dependabot are table stakes. The subtler control is the lockfile: it pins the exact resolved versions so that a fresh install cannot silently pull a newly-published malicious patch release. In CI, npm ci installs strictly from the lockfile, which is why it belongs in a pipeline while npm install does not.

Detection

A09 from section 01 lands here. Log authentication outcomes, authorization denials, and privilege changes as structured events with a correlation id — and log the denials, since a spike in 403s is what an enumeration attack looks like from the inside. Never log the secret itself: not passwords, not tokens, not full card numbers, not the raw request body of an auth endpoint. Logs get shipped to third parties, read by support staff, and retained far longer than anyone intends.

"How do you keep secrets out of a deployed application?"

"Three layers. They never enter the repository, because Git history is append-only — once a key is pushed, rotation is the only real remediation, and I would treat deleting it in a later commit as a false fix. At runtime they come from the environment, with care about the client boundary: anything a bundler inlines into browser code is published no matter what the variable is called. And for anything with real blast radius I want a managed store, less for the encryption than for rotation and the audit trail — being able to answer who read a value and when, and to change it without a redeploy. Underneath all of it, the credential itself should be scoped down, because how bad a leak is depends mostly on what that credential was allowed to do."

Security in Your Projects

How to frame your experience.
Gaza40+: Implemented strict RBAC (Role-Based Access Control) across 5 roles. Permissions are validated on the server on every request, *never* trusted from the client payload. Enforced regional isolation at the database query level.
Eudoro: Handled payment webhook security using Razorpay signature verification to prevent spoofed successful payment events. Used immutable ledger patterns for seller payouts to prevent race condition double-spends.
