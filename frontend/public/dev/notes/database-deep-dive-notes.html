01
Internals

PostgreSQL Internals

How Postgres actually manages data.

MVCC (Multi-Version Concurrency Control)

Readers don't block writers, and writers don't block readers. Postgres creates a new version of a row on UPDATE rather than overwriting it in place.

Vacuuming

Because MVCC leaves old row versions (dead tuples) behind, VACUUM reclaims this space. Auto-vacuum runs in the background but heavy update workloads might require manual tuning.

WAL (Write-Ahead Logging)

Changes are written to a sequential log *before* being applied to data pages. Guarantees durability (the D in ACID) and is used for replication and point-in-time recovery.

Connection Pooling

Postgres creates a heavy OS process per connection. Connection poolers (like PgBouncer or Prisma Accelerate) multiplex many lightweight client connections onto fewer real database connections.

02
Performance

Indexing Deep-Dive

Finding data without scanning the whole disk.

B-Tree

The default index type. Good for equality (=) and range queries (<, >). O(log N) search complexity.

GIN & GiST

Generalized Inverted Index. Essential for full-text search and JSONB containment queries (finding a key inside a JSON blob).

Partial Indexes

Indexes only a subset of rows (e.g., WHERE is_active = true). Much smaller index size, faster to scan and update.

"Why is my index not being used?"

"The query planner might decide a sequential scan is faster if the table is small or if the query returns a large percentage of the table. Also, using functions on the indexed column (like LOWER(email)) disables the index unless an Expression Index was created. Check with EXPLAIN ANALYZE."

Row Locking & Deadlocks

When updating a wallet balance (like in Eudoro), always use SELECT ... FOR UPDATE to lock the row and prevent race conditions (Lost Updates). If two transactions lock rows in different orders, a deadlock occurs. Always acquire locks in a consistent order.

04
Design

Data Modeling

Normalization is not a style preference. It is a defence against a specific class of bug.

Most explanations of normal forms start with the rules, which is why most people forget them. Start with the problem instead. Suppose orders are stored with the customer's address copied into each row. Nothing is wrong yet. Then the customer moves. Now you have to update every order row, and the moment one update fails or one row is missed, the database holds two different answers to the same question and neither is marked wrong. That is an update anomaly, and normalization exists to make it structurally impossible rather than merely unlikely.

Once you see it that way the forms are almost obvious. Each one removes a way for the same fact to be recorded twice:

FormRuleThe anomaly it removes
1NFEach column holds one value, not a list.You cannot query, index, or constrain the third item in a comma-separated string. Everything downstream gets harder.
2NFNon-key columns depend on the whole key, not part of it.On a composite key, a column that depends on only half of it gets duplicated across every row sharing that half.
3NFNon-key columns depend on the key and nothing else.Storing city and city_population together means the population is repeated per city, and updating it means finding every row.

The practical summary interviewers are listening for: every fact should live in exactly one place. 3NF is the default for anything transactional. If you can say why in terms of anomalies rather than reciting the definitions, you are already ahead.

And then you denormalize on purpose

Normalization optimizes for write correctness; it costs you joins on read. Denormalizing — caching a comment_count on the post, copying the product name onto the order line — is a legitimate, deliberate trade: you accept the duplication and take on the job of keeping the copies honest. The distinction that matters is intentional denormalization with a plan for consistency versus an accident. Order lines are the classic case where duplication is not even a compromise: you genuinely want the price as it was at purchase, not the current price. That is not a stale copy, it is a historical fact.

Relationships

One-to-many

The foreign key lives on the many side. An order has many line items, so order_id sits on the line item. Put an index on that column — Postgres does not create one automatically for a foreign key, and its absence is a very common cause of slow joins and of DELETEs on the parent table that take forever.

Many-to-many

Needs a third table. Students and courses become enrollments, with a composite primary key on both ids to prevent duplicates. The useful realization is that the join table almost always grows attributes of its own — enrolled_at, grade — which means it was a real entity all along.

One-to-one

Usually a sign the columns belong in one table. It earns its keep when a group of columns is rarely read, or is large, or has a different security profile — splitting sensitive KYC fields into their own table lets you grant access to it separately.

Self-referencing

Hierarchies: an employee's manager_id pointing back at the same table, categories with parents. Reading the whole tree needs a recursive CTE (WITH RECURSIVE), which is worth practising once so it is not a surprise.

Choices that are hard to reverse

Some modeling decisions can be changed with a migration. These ones tend to leak into application code everywhere and become expensive to undo, so they are worth getting right early.

DecisionDefaultReasoning
Primary keySurrogate (generated), not naturalNatural keys — email, phone, ISBN — change, and when they do you are updating every referencing row. A meaningless id never changes because it never meant anything.
Sequential vs UUIDDepends on exposureSequential integers are compact and index well but leak volume and are enumerable in URLs. UUIDv4 is random, which hurts B-tree locality on insert; UUIDv7 is time-ordered and gets most of the locality back.
MoneyInteger minor units, or NUMERICNever floating point. 0.1 + 0.2 is not 0.3 in binary floating point, and that error compounds across a ledger. Store paise or cents as an integer, or use exact NUMERIC.
TimestampsTIMESTAMPTZ, always UTCTIMESTAMP without a zone stores a wall-clock reading with no way to know what it meant. Convert to local time at the edge, for display only.
DeletesSoft delete when history mattersA deleted_at column preserves auditability, but it now has to appear in every query and every unique constraint. Do it deliberately, not reflexively.
NullableNOT NULL unless null means somethingNULL means "unknown", and it propagates through comparisons in ways that surprise people. If the column always has a value, say so and let the database enforce it.
Analogy

A normalized schema is a library where every book has one shelf. Denormalizing is putting popular titles on a display stand by the door as well — genuinely faster for the reader, and now you own the problem of keeping the display in sync with the shelf. Worth doing knowingly. Painful when it happens by accident.

"How would you approach modeling a new feature's schema?"

"I start from the facts and the access patterns rather than from the tables. What are the real entities, what is genuinely true about each one, and which of those facts change independently — because anything that changes independently wants its own row, otherwise I get update anomalies where the same fact is stored twice and can disagree with itself. I normalize to 3NF as the default and only denormalize where a read path demands it, deliberately, with an answer for how the copies stay honest. Then I decide the things that are expensive to change later: surrogate keys, TIMESTAMPTZ in UTC, integer minor units for money, NOT NULL wherever null would not carry meaning. Those are the ones that leak into application code everywhere if I get them wrong."

Replication & Scaling

In the order you should actually reach for them, which is not the order people describe them.

The useful framing is that scaling a database is a sequence of steps that each buy time and each cost something, and the discipline is not skipping ahead. Almost every "we need to shard" conversation is really a missing index or a connection pool that was never configured. Work the list in order, and be able to say why the earlier steps were exhausted.

Fix the queries

Scale up
Cache
Read replicas

Why connection pooling comes so early

This is the step most often skipped and it is specific to how Postgres is built. Postgres forks a full OS process per connection, and each one reserves several megabytes before it does any work. A few hundred connections is therefore not a large number to a Node process but is a serious number to the database. Serverless makes it sharper still: every concurrent function instance wants its own connection, so an autoscaling API can exhaust the connection limit while the CPU sits near idle.

A pooler — PgBouncer, or a managed equivalent — keeps a small set of real backend connections and multiplexes many client connections onto them. In transaction pooling mode a backend is handed out for the duration of a transaction and then returned, which is what lets a handful of real connections serve a large number of callers. The catch worth knowing: transaction mode breaks anything that assumes session state across statements — session-level SET, advisory locks held between transactions, some prepared-statement patterns.

Read replicas and the lag you inherit

A replica streams the primary's write-ahead log and applies it. Reads scale out; writes still all go to the primary, which is why replicas help read-heavy workloads and do nothing for write-heavy ones.

The part that actually shows up in production is replication lag. Default replication is asynchronous: the primary commits and acknowledges without waiting for replicas, so a replica is some milliseconds — occasionally seconds, under load — behind. That produces the read-your-writes problem, and it is worth being able to describe concretely: a user updates their profile, the write goes to the primary, the redirect issues a read that lands on a lagging replica, and the app shows them their old data. They retry, it works, and the bug is unreproducible for you.

Three ways out, in increasing cost

Route reads after writes to the primary — pin a user to the primary for a few seconds after any write. Cheap and covers the common case. Wait for the replica to catch up — track the WAL position of your write and only read from a replica that has reached it. Precise, more plumbing. Synchronous replication — the primary waits for a replica to confirm before acknowledging. No lag, but every write now pays the round trip, and if the replica is unhealthy your writes stall. That last trade is the CAP theorem showing up in a config flag rather than a diagram.

Partitioning versus sharding

These get used interchangeably and they are not the same thing. Partitioning splits one big table into smaller physical pieces inside a single database — usually by range, most often by time. The database knows about the partitions, so WHERE created_at >= … lets the planner skip whole partitions, and dropping last year's data becomes an instant DROP of a partition instead of a DELETE of millions of rows. It buys you a great deal and costs almost nothing architecturally.

Sharding splits data across separate database servers that do not know about each other. It is the only step that removes a write ceiling, and it is qualitatively harder than everything before it, because the guarantees you have been relying on stop being free:

Cross-shard joins

Stop existing. If two tables live on different servers, joining them becomes application code fetching from both and merging — with no query planner helping and no transactional view.

Transactions

ACID holds within a shard. Across shards you are into two-phase commit or, more commonly, sagas and compensating actions — eventual consistency with explicit undo steps.

The shard key is forever

Choosing it is the whole decision. Shard by tenant and a single large tenant becomes a hot shard. Shard by hash and range queries fan out to every server. Changing the key later means moving all the data.

Rebalancing

Adding a server means redistributing data while serving traffic. Consistent hashing limits how much moves; it does not make the operation trivial.

Analogy

Read replicas are photocopies of the ledger — anyone can read one, but a copy made a moment ago may not show the last entry. Partitioning is filing the same ledger into one binder per month. Sharding is opening a second branch office with its own ledger: now nothing reconciles automatically, and "how much did we sell?" becomes a project.

"The database is struggling. What do you do?"

"I would want to know what 'struggling' means before touching topology, because the answer is usually much earlier in the list than people expect. First I look at whether it is a query problem — EXPLAIN ANALYZE on the slow paths, a check for sequential scans and for foreign keys with no index. Then connections, which is the step most often skipped: Postgres forks a process per connection, so an autoscaling API can exhaust the limit while CPU is idle, and a pooler in transaction mode fixes that without changing the schema. After that, caching and read replicas if reads dominate — and if I add replicas I have to handle read-your-writes, which I would usually do by pinning a user to the primary briefly after a write. Partitioning by time if one table has grown unbounded. Sharding last, because it is the point where cross-table joins and transactions stop being free, and I would want to be sure a write ceiling is genuinely the constraint before paying that."

NoSQL

MongoDB

Flexible schema and document modeling.

Embedding vs Referencing

Embed data that is queried together and doesn't grow infinitely (e.g., user preferences).
Reference (like foreign keys) for large, unbounded lists (e.g., user posts).

Aggregation Pipeline

Powerful framework for data transformation. Stages like $match, $group, $lookup (joins), and $project are processed in sequence.

Project Applications

How you applied databases in your real work.

Eudoro (PostgreSQL + Prisma)

Used Postgres for strong relational integrity between Sellers, Buyers, and Orders. The immutable wallet ledger requires ACID transactions to ensure sellers are paid correctly only after delivery.

Gaza40+ (MongoDB)

MongoDB's flexible schema allowed handling varied document requirements for students without massive schema migrations. Used aggregation pipelines for complex case tracking.

Forever Yours / Shaza (MongoDB Atlas Vector Search)

Utilized MongoDB Atlas for native vector search capabilities alongside standard application data, enabling the RAG pipeline to retrieve relevant chat memories instantly.
